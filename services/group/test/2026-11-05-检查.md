# 2026-11-05 group 检查

## 范围

看 group 服务自己的表、本地缓存和热查询。不改线上库 `suim`。现有功能测试 `go test ./services/group/ ./services/group/internal/... -count=1` 通过，约 1.4 秒。

## 数据放在哪

群资料、成员、入群申请、成员版本、入群版本都在 group 自己的库。用户资料通过 user 服务的接口取，不查 user 表。通知通过 msg 发出，会话序号通过 conversation 写。进程内测试用的是假用户名单，不打这些服务。

## 缓存

本地缓存有三样：群资料、单个成员、整个成员 ID 列表。槽 100，每槽 2000，成功 300 秒，失败 5 秒。改成员或改群时删掉对应键，并用 Redis 频道 `suim:group:cache:delete` 通知其他 group 进程。

Redis 不存群资料本身。成员分页、已加入的群、入群申请、增量日志都不进本地缓存。

## 执行计划

下面是 `suim_group_bench` 上 5000 名成员、201 个已加入群、2000 条待处理申请时的计划。产品配置里普通群上限 200 人，超级群上限 1000 人。这场用 SQL 直接灌了 5000 人，是为了把排序成本看出来。

| 查询 | 计划 |
| --- | --- |
| 按群 ID 取群 | 主键，`const` |
| 按群统计人数 | 主键，`ref`，`Using index` |
| 成员第一页、深分页、全量成员 ID | 主键，`ref`，然后 `Using filesort` |
| 单个成员 | 主键，`const` |
| 已加入群的人数 | `idx_group_member_user_id`，`Using index` |
| 已加入群第一页 | 同一个索引，然后 `Using filesort` |
| 某群待处理申请第一页 | 主键，`ref`，`Using where; Using filesort` |
| 成员版本日志，版本之后 50 条 | `idx_group_member_version_log_version`，`range` |
| 某人管理的群 | `idx_group_member_user_id`，`Using where` |

成员列表的排序是 `role_level DESC, join_time ASC, user_id ASC`。现有的 `(group_id, role_level)` 带不走 `join_time`，所以 5000 行要在内存里排。深分页只比第一页慢大约 2 毫秒，时间主要花在这次排序，不是花在偏移上。

已加入的群按 `join_time DESC, group_id ASC` 排，索引只有 `user_id`，201 行也要排序。申请按 `req_time DESC` 排，主键是 `(group_id, user_id)`，2000 行同样要排序。

群资料每次未命中缓存时还要再查人数和群主。命中本地缓存后这两次都省掉。
