## 一、先把「顺序」定义清楚

讨论顺序性之前必须区分三种「序」，很多设计分歧都源于混用：

| 序           | 含义                         | 是否可保证           |
| ------------ | ---------------------------- | -------------------- |
| 真实发生序   | 物理世界里谁先按下发送键     | 不可知（无全局时钟） |
| 服务端接收序 | 请求到达服务端并被受理的先后 | 可保证，且是唯一权威 |
| 客户端展示序 | 用户屏幕上从上到下的排列     | 必须等于服务端接收序 |

**生产共识：IM 只承诺「单会话内、以服务端受理序为准」的全序（Total Order），不承诺跨会话有序，也不承诺与用户主观的「我先发的」一致。**

这条定义直接决定了后面所有设计——一旦承认服务端序是唯一真相，客户端本地时间戳、本地插入位置就都只能当草稿。

------

## 二、乱序的六个来源

1. **多路并发上行**：客户端多条长连接 / HTTP 并发，先发的包后到。
2. **服务端多线程**：网关收到后丢进线程池，调度不确定。
3. **MQ 分区打散**：Kafka/RocketMQ 只保证单分区有序，同一会话的消息被轮询分到不同分区就废了。
4. **超时重传**：M1 超时重发，M2 已正常入库，结果 M2 在前。
5. **推送通道无序**：APNs/FCM/自建长连接的下行推送本身不保证到达顺序，且可能重复。
6. **多端同时写**：手机和 PC 同时发消息；或者群里几百人同时说话。

------

## 三、总体架构：三层防线

```text
客户端 ──► 接入层(会话亲和) ──► 序号分配(串行化) ──► MQ(按会话分区) ──► 存储(会话+seq主键)
   ▲                                                                        │
   └──────────── 按 seq 排序 / 补洞 / 去重 ◄──── 推拉结合同步 ◄──────────────┘
```

核心思想一句话：**服务端给每个会话分配严格单调递增的 seq，把 seq 作为消息的唯一排序依据；管道各环节都以 `conversationId` 做亲和路由保证不跨道；客户端不信任推送顺序，只信任 seq 并主动补洞。**

## 四、服务端 seq：整套方案的地基

### 4.1 属性要求

- **会话内单调递增**：必须。
- **会话内尽量连续（无空洞）**：强烈推荐。连续才能让客户端精确判断「我漏了几条」。
- **全局唯一 msgId 独立于 seq**：msgId 可以用 Snowflake，但 **seq 绝对不能用 Snowflake**——Snowflake 只保证趋势递增，多机时钟回拨会直接产生倒退，且无法保证同会话连续。

### 4.2 生成方案对比

| 方案                                          | 连续性               | 性能           | 适用                                 |
| --------------------------------------------- | -------------------- | -------------- | ------------------------------------ |
| DB 行锁 + 自增（`UPDATE conv SET seq=seq+1`） | 严格连续             | 低（单行热点） | 中小规模、强一致要求                 |
| Redis `INCR conv:{id}:seq`                    | 严格连续             | 高             | 主流选择，需解决持久化               |
| 号段模式（一次取 1000 个到内存）              | 连续但重启会有大空洞 | 极高           | 写扩散收件箱、可容忍空洞             |
| 会话内 Actor 单线程计数                       | 严格连续             | 高             | 内存态会话管理（Skynet/Erlang 风格） |

**生产推荐：Redis INCR 为主 + 异步落库校准。**

关键细节：

- Redis 必须开 AOF `appendfsync everysec`，并接受「最多丢 1 秒」的风险；或用 Redis Cluster 单 slot 主从 + 故障后从 DB 最大值恢复。
- **恢复时的 fencing**：主从切换后新主可能给出比旧主更小的 seq。解决办法是给计数器加 `epoch`，seq 编码为 `(epoch << 40) | counter`，切换时 epoch+1，客户端比较时天然单调。或者直接规定：切换后从 DB 中该会话 `max(seq)` 起步并跳过一段安全区间（如 +10000）。

### 4.3 分配点必须串行化

**绝不能「先并发处理业务，再各自去拿 seq」**，否则拿到 seq 的顺序和入库顺序会错位。正确做法是：

```text
接入层收到消息
  → 幂等检查(clientMsgId 是否已存在)
  → 【串行点】分配 seq        ← 这里就是「受理时刻」
  → 组装消息体(msgId, convId, seq, content, serverTime)
  → 写 MQ / 写存储
  → 返回 ACK(带 seq) 给发送方
```

串行点的实现方式（按并发量选）：

- **会话亲和路由**：网关按 `hash(conversationId)` 把同一会话的所有请求打到同一台机器的同一个单线程执行器（`Map<convId, SingleThreadExecutor>` 或 Actor）。这是最干净的做法，无锁。
- **分布式锁**：`SET lock:conv:{id} NX PX 3000`。简单但延迟高、有死锁风险，只适合低并发。
- **DB 乐观锁**：`UPDATE conv SET seq=? WHERE id=? AND seq=?`，失败重试。

> 单聊和中小群（<500 人）用亲和路由完全够。万人大群是另一套问题（见第八节）。

## 五、消息管道：不要让 MQ 毁掉顺序

- **分区键固定为 `conversationId`**（不是 userId，不是 msgId）。Kafka 同一 key 落同一 partition，partition 内天然有序。
- **消费端按 partition 单线程消费**，或用 `hash(convId) % workerNum` 把同一会话固定给同一 worker。**严禁在消费端开并发线程池处理同一 partition 的消息。**
- **分区扩容是隐形炸弹**：partition 数从 64 变 128，同一个 convId 会重新映射，扩容瞬间新旧分区并行消费 → 乱序。对策：一开始就规划足够多的分区（如 512）；必须扩容时，选低峰期、先停消费 → 等 lag 清零 → 扩容 → 重启，或者临时把该会话的消息落到「缓冲表」重排后再投递。
- **MQ 重试会打乱顺序**：某条消息处理失败进重试队列，后面的先成功了。对策：消费失败时**不要跳过**，而是本地阻塞重试有限次，仍失败则整个 partition 暂停（fail-fast）并告警，人工/自动补偿。宁可延迟，不可乱序。

## 六、存储层设计

主键必须是 `(conversation_id, seq)`：

```sql
CREATE TABLE message (
  conversation_id BIGINT NOT NULL,
  seq             BIGINT NOT NULL,
  msg_id          VARCHAR(32) NOT NULL,   -- 全局唯一，Snowflake
  client_msg_id   VARCHAR(64) NOT NULL,   -- 客户端幂等键
  sender_id       BIGINT NOT NULL,
  content         BLOB,
  server_time     BIGINT NOT NULL,        -- 仅用于展示，不用于排序
  status          TINYINT,                -- 正常/已撤回/已删除
  PRIMARY KEY (conversation_id, seq),
  UNIQUE KEY uk_client (sender_id, client_msg_id)
);
```

- 主键设计让「拉取会话最近 N 条」变成一次范围扫描：`WHERE conversation_id=? AND seq<? ORDER BY seq DESC LIMIT 50`，性能极好。
- HBase/Cassandra 场景：rowkey = `convId`（可加盐但要保证同会话同 region），column qualifier = seq 的定长补零字符串，天然按 seq 排序。
- `uk_client` 唯一索引是幂等的最后一道防线，防止重传产生两条 seq 不同的重复消息。

## 七、写扩散 vs 读扩散下的顺序性

**读扩散（会话维度存一份，成员读同一份）**

- 只有一个 `convSeq`，简单，顺序性天然统一。
- 未读数需要额外维护每人的 `readSeq`。
- 适合：群聊、大群。

**写扩散（每个用户一个收件箱 inbox）**

- 存在**两级 seq**，必须分清：
  - `convSeq`：会话内的逻辑顺序，来自会话计数器。
  - `inboxSeq`：某用户收件箱的物理顺序，来自该用户自己的计数器（可用号段模式）。
- **展示排序用 `inboxSeq`，补洞/去重/已读判断用 `convSeq`。**
- 写扩散下同一会话的消息进入不同用户 inbox 的时刻不同，所以「A 看到的第 5 条」和「B 看到的第 5 条」inboxSeq 不同，但 convSeq 相同 → 两端展示顺序一致。这正是两级 seq 的价值。
- 适合：单聊、小群，读性能极佳。

微信是典型的写扩散（Timeline/收件箱模型），大群场景则会退化为读扩散以控制写放大。

------

## 八、高并发群聊的热点问题

万人群一秒几千条消息，单会话串行分配 seq 会成瓶颈。工程上的取舍：

1. **批量分配**：一次 `INCRBY` 拿 100 个 seq，在会话 Actor 内存里逐个发放。延迟降到微秒级，代价是重启会有空洞。
2. **接受「稀疏 seq」**：不要求连续，只要求单调递增。客户端补洞逻辑从「死等 seq+1」改成「拉取 `(localMax, serverMax]` 区间」。这是绝大多数大厂的实际选择。
3. **超大群降级**：不保证全局严格序，只保证「同一发送者的消息有序」（发送者维度分区），展示时按服务端时间粗排。这是有意的产品妥协，需要明确告知业务方。
4. **削峰**：万人群的「全员同时@」类广播消息走独立通道，不占用会话 seq 序列。

## 九、客户端：真正的顺序保障发生在这里

推送不可信，所以客户端必须自己做三件事：**排序、去重、补洞**。

### 9.1 推拉结合

```text
服务端:  推送一个轻量通知 {convId, latestSeq}   // 甚至可以不推内容
客户端:  收到通知 → if (latestSeq > localMaxSeq) 拉取 (localMaxSeq, latestSeq]
```

推送丢了不影响正确性（有兜底轮询 / 前台切换时全量校准），推送乱序也不影响（拉取时按 seq 排序）。

### 9.2 补洞与乱序缓冲

```java
void onMessage(Msg m) {
    if (dedup.contains(m.msgId)) return;          // 去重
    if (m.seq <= localMaxSeq) {                   // 补洞：填补历史空缺
        db.insert(m); dedup.add(m.msgId);
        ui.insertAtPositionBySeq(m);
        return;
    }
    if (m.seq == localMaxSeq + 1) {               // 连续，直接前进
        db.insert(m); localMaxSeq = m.seq;
        drainReorderBuffer();                     // 冲掉后续可连续的
    } else {                                      // 出现空洞
        reorderBuffer.put(m.seq, m);
        schedulePull(localMaxSeq + 1, m.seq - 1); // 主动拉取缺失段
        if (bufferWaitTime > 3s) {                // 超时容忍：先显示，避免卡屏
            localMaxSeq = m.seq; flushBuffer();
            markSeqRangeDirty(localMaxSeq, m.seq); // 后台静默补齐
        }
    }
}
```

关键权衡：**严格等洞会让用户看到「消息卡住不出」**，所以生产上普遍采用「3 秒超时先上屏 + 后台补齐」的策略，UI 顺序可能在极短时间内微调一次（新消息插入到中间而非末尾），这是可接受的。

### 9.3 发送方自己的消息回位

用户点发送 → 本地立刻插一条「发送中」占位在列表末尾 → 服务端 ACK 返回真实 seq → **必须按 seq 重新定位**，而不是保留在末尾。

否则经典的「双方各说各话」就出现了：A 和 B 几乎同时发消息，A 端把自己的排在最后，B 端也把自己的排在最后，两端看到的对话顺序不一致。统一以服务端 seq 重排后，两端视图收敛。

### 9.4 客户端本地时钟一律不可信

- 不用客户端时间戳排序，不用它做 seq。
- 服务端时间戳只用于 UI 上「14:32」这类展示，以及「时间分割线」。
- 客户端时间偏移只用于估算 RTT、超时判断。

## 十、幂等与重传（顺序性的孪生问题）

乱序和重复往往同时出现，必须一起解：

- **客户端生成 `clientMsgId`**（UUID），重传时保持不变。
- 服务端在分配 seq **之前**先查 `clientMsgId`：命中则直接返回上次的 seq（幂等 ACK），不重复分配。
- **ACK 必须带 seq**，客户端据此把「发送中」转为「已发送」并回位。
- 语义上做到 `at-least-once 投递 + clientMsgId 去重 = effectively-once`。不要追求 exactly-once，代价过高。

## 十一、特殊消息类型的顺序处理

- **撤回 / 编辑**：不修改原消息的 seq，而是新增一条「操作事件」（带 `targetMsgId`）。客户端按 seq 顺序应用事件流，这样即使操作事件晚到也能正确回放。修改原记录会让多端同步无法判断谁新谁旧。
- **已读回执**：走独立通道，只传 `readSeq` 水位，不进消息序列。
- **正在输入 / 信令**：不进 seq，可丢可乱序。
- **系统消息（入群、退群）**：**必须进 seq**。否则会出现「某人在退群消息之后还发出了消息」这种因果错乱。这是很多 IM 的经典 bug。
- **消息回复引用（quote）**：引用关系依赖 seq 已存在，客户端要处理「被引用消息尚未同步到本地」的情况，先占位后补齐。

## 十二、一致性校验与故障兜底

生产系统必须有「自我发现乱序」的能力：

1. **对账任务**：定时扫描每个活跃会话，校验 seq 是否存在空洞、是否存在重复；发现空洞则从 MQ/备份补齐或标记为永久丢失（占位「消息已过期」）。
2. **水位线机制**：每个会话维护 `commitSeq`（已持久化最大 seq）与 `assignSeq`（已分配最大 seq）。若 `assignSeq - commitSeq` 长期不收敛，说明有消息卡在管道里，告警。
3. **客户端全量校准**：App 冷启动、切前台、网络恢复时，拉取每个会话的 `latestSeq` 与本地比对，差异大则触发增量同步，差异极大（如 > 5000 条）则走「清空重下」路径。
4. **混沌测试**：注入网络延迟抖动、乱序、丢包、重复包、服务端实例 kill、Redis 主从切换、Kafka 分区扩容，验证最终两端视图一致。这是顺序性设计的验收标准，不做就等于没做。

------

## 十三、一句话总结每层的职责

- **接入层**：按会话亲和，把并发变串行。
- **序号层**：分配严格单调递增的 seq，这是全系统的「时间轴」。
- **管道层**：以 `conversationId` 为分区键，永不跨道，失败不跳过。
- **存储层**：`(convId, seq)` 做主键，`clientMsgId` 做幂等唯一键。
- **同步层**：推拉结合，推送只是「提示去看」，拉取才是「事实来源」。
- **客户端**：按 seq 排序、去重、补洞、回位，本地时钟和推送顺序一律不信。

> 顺序性的本质不是「让包按顺序到达」（做不到），而是**给每条消息一个全局共识的编号，让所有端都能独立地把乱序数据重排成同一个视图**。
