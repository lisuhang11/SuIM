# IM 全文检索：SQLite FTS 与微信本地实践

做 IM 久了会发现：消息存得好、推送稳，用户仍会问「为什么搜聊天记录这么慢」。答案往往不在主消息表，而在有没有一层专门的**全文检索（Full-Text Search，FTS）**。

微信客户端本地目录 `xwechat_files` 里，除了 `message_*.db`、`contact.db`、`favorite.db` 这些业务库，还单独挂着：

| 库 | 作用 | 某真实账号体量（约） |
| --- | --- | --- |
| `message_fts.db` | 搜聊天记录 | **~62MB** |
| `contact_fts.db` | 搜联系人 / 群成员 | ~5MB |
| `favorite_fts.db` | 搜收藏 | ~100KB |

它们是**索引库**，不是又一份聊天正文。正文仍在主库；FTS 只回答「哪些文档包含这些词」，再回表拼气泡。

本文把三件事讲清楚：**FTS 是什么、SQLite 里怎么实现、微信端怎么落地**；最后对照 SuIM，看服务端还缺哪一层。

------

## 一、FTS 是什么：不是 LIKE，是倒排索引

### 1.1 业务场景

用户在顶部搜索框输入「项目总结」，期望：

- 命中哪些聊天记录、哪个会话；
- 命中哪些联系人 / 群；
- 命中哪些收藏；
- 最好还能相关度排序、中文分词、（可选）拼音。

聊天历史以十万、百万条计时，若没有专用索引，体验会立刻垮掉。

### 1.2 LIKE 为什么扛不住

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| `LIKE '%项目总结%'` | 逐行字符串匹配 | 数据一大就全表扫；中文词边界、多关键词、拼音都很难 |
| **FTS** | 先切词，再建「词 → 出现在哪些行」的索引 | 查时走索引，再按需回表 |

类比：书后面的**索引页**，不是从第一页翻到最后一页。

### 1.3 倒排索引（inverted index）

正向：文档 → 词。  
倒排：词 → 文档（以及位置）。

```text
原文：
  消息A: "明天开会讨论项目"
  消息B: "项目进度如何"

切词后倒排：
  明天 → [A]
  开会 → [A]
  讨论 → [A]
  项目 → [A, B]
  进度 → [B]
  如何 → [B]

搜「项目」→ 直接得到 [A, B]
```

每个 token 通常还会记：行号、列号、在字段内的出现位置。有了位置，才能做相关度、短语匹配和高亮。

**一句话：FTS = 分词 + 倒排索引 + MATCH 查询；主消息表继续只负责有序存储与同步。**

## 二、SQLite 里怎么实现：FTS5 虚拟表

### 2.1 模块定位

SQLite 提供 FTS3 / FTS4 / FTS5 扩展。近年微信端侧实践与公开逆向，消息搜索多落在 **FTS5**。

FTS5 以**虚拟表**形式存在：你 `CREATE VIRTUAL TABLE ... USING fts5(...)`，对外像一张普通表可 `INSERT` / `SELECT`；对内维护倒排段（segment）和一组影子表。

### 2.2 建表示意（接近微信消息 FTS）

公开逆向中可见类似结构（示意，版本会变）：

```sql
CREATE VIRTUAL TABLE message_fts_v4_0 USING fts5(
  tokenize = 'MMFtsTokenizer disable_pinyin',  -- 自研分词器
  acontent,                                    -- 真正被索引的文本
  message_local_id UNINDEXED,
  sort_seq         UNINDEXED,
  local_type       UNINDEXED,
  session_id       UNINDEXED,
  sender_id        UNINDEXED,
  create_time      UNINDEXED
);
```

字段分工：

| 列 | 含义 |
| --- | --- |
| `acontent` | 可搜正文（聊天文本等），参与分词与倒排 |
| `UNINDEXED` 列 | **不参与分词**，只跟着存，方便结果回跳真实消息（会话、本地 id、时间、类型） |
| `tokenize = ...` | 如何把字符串切成 token；中文质量几乎全靠它 |

### 2.3 影子表（你在 sqlite_master 里会看到）

FTS5 常见附属对象名：

| 后缀 | 作用 |
| --- | --- |
| `*_data` / `*_idx` | 倒排段与词项索引 |
| `*_content` | 文档内容副本（或外置 content 模式） |
| `*_docsize` | 文档长度等，用于打分 |
| `*_config` | 模块配置 |

公开解析工具也明确：名字以 `_data`、`_idx`、`_content`、`_config`、`_docsize` 结尾的，通常是 FTS 支撑表，**不是**聊天消息本身。

### 2.4 查询形态

```sql
SELECT *
FROM message_fts_v4_0
WHERE message_fts_v4_0 MATCH '项目'
ORDER BY rank;   -- 可按相关度排序
```

等价写法还有 `= '项目'` 或表值函数语法。默认大小写不敏感；无 `ORDER BY` 时返回顺序任意，产品层一般要自己定排序（相关度、时间、会话）。

### 2.5 写入时发生了什么

每次事务写入的内容，FTS5 会落成独立的 b-tree 段（segment）。段里保存：本次写入中每个词的 rowid、列号、出现位置——也就是这一批的倒排。

多次写入 → 多个 segment → 查询时要分别查再合并。**segment 越多，查询越慢**，因此生产上要做合并（merge）、控制分区、避免无意义高频写入把索引打散。微信 iOS 侧公开复盘过从 FTS3 升 FTS5、以及索引合并与写入路径的优化，根因就在这里。

## 三、中文分词：IM 搜索的真正门槛

英文可以靠空格；中文不行。

- 没有分词：搜「项目」可能对不上「我们的项目进度」。
- 分词太碎：索引膨胀、噪音大。
- 分词太粗：召回差。

微信使用自研分词器（逆向里常见名 **`MMFtsTokenizer`**），可配置是否启用拼音等能力。联系人搜索还要覆盖昵称、备注、群名等字段，分词与归一化规则和聊天记录不完全相同，所以拆成独立的 `contact_fts`。

**分词质量 = 搜得到 / 搜不到；倒排结构只是容器。**

## 四、微信本地怎么落地

以下结合 Windows 新版微信数据目录 `xwechat_files/<账号>/db_storage/` 的观察，以及公开技术文章 / 逆向文档。库文件本身多为 SQLCipher/WCDB 加密，下文谈的是**架构角色**，不是解密后的业务内容。

### 4.1 索引与正文分离

```text
message_0.db / message_1.db / ...   ← 聊天权威存储（按会话表 Msg_<md5> 等组织）
message_fts.db                      ← 仅全文索引

contact.db                          ← 联系人权威
contact_fts.db                      ← 联系人搜索索引

favorite.db                         ← 收藏权威
favorite_fts.db                     ← 收藏搜索索引
```

好处：

1. 索引膨胀、重建、合并不直接拖垮主聊天读写路径；
2. 主库损坏可尝试重建 FTS；FTS 损坏时聊天仍可读，只是搜索降级；
3. 搜索与「按会话 + seq/时间拉历史」职责分离。

### 4.2 消息 FTS 再分区

逆向中常见 `message_fts_v4_0` … `message_fts_v4_3` 一类分区虚表，并辅以 `message_fts_v4_aux_*`（按 `session_id + message_local_id + sort_seq` 定位）。目的是控制单索引体积，降低 segment 过多带来的读写压力——和主库把消息拆成 `message_0/1/2.db` 是同一类「切分」思路，切的是**索引**，不是再存一份聊天。

### 4.3 三类搜索各走各的索引

微信团队公开复盘过（约 2021，iOS）升级前的状态：

| 场景 | 旧做法 | 现状方向 |
| --- | --- | --- |
| 聊天记录 | SQLite FTS3 | FTS5 + 自研分词 + 工程优化 |
| 联系人 | 内存遍历属性做字符串匹配 | 独立 `contact_fts` |
| 收藏首页 | `LIKE` | 独立 `favorite_fts` |

顶部全局搜索会分别打这几路，再按业务合并展示（联系人 / 聊天记录 / 收藏 / …）。

### 4.4 读写完整链路（简化）

```text
发/收一条文本消息
  → 写入 message_N.db（权威聊天记录）
  → 抽取可搜文本 → 分词 → 写入 message_fts（倒排）
  → 可选：更新 session.db 里的最后一条摘要（与 FTS 无关）

用户输入「项目」
  → MATCH message_fts
  → 得到 message_local_id / session_id / sort_seq …
  → 回 message_*.db 取完整气泡
  → 媒体仍走 message_resource / hardlink / msg/ 文件树
```

要点：**FTS 命中的是索引文档；UI 气泡、图片、引用仍要从主库和资源层拼。** `session.db` 管会话列表与未读摘要，不负责完整历史，也不替代 FTS。

### 4.5 为什么 message_fts 能到几十 MB

索引体积大致随下面因素涨：

- 可搜消息条数；
- 平均文本长度（长文、链接、文件名都会进索引）；
- 分词后的词项密度与位置信息；
- 分区与影子表开销；
- 删除/撤回后未及时合并造成的空洞与冗余。

所以看到某账号 `message_fts.db` ≈ 62MB，含义是：**本地为「词 → 消息」建了一份相当厚的倒排**，不是又存了 62MB 原图。附件实体仍在 `msg/attach`、`msg/file` 等目录，由 `hardlink` / `message_resource` 索引。

### 4.6 产品层作用

用户侧：

1. 全局搜聊天记录；
2. 搜联系人 / 群；
3. 搜收藏；
4. 会话内搜索（同一套索引加 `session_id` 过滤）。

工程侧：

- 查找成本接近「跟关键词相关的索引规模」，而不是「全部消息行数」；
- 支持多词、相关度、（实现允许时）拼音；
- 主库专注有序历史；搜索走专用索引；
- **离线可用**——不依赖服务端搜索集群即可秒开。

没有这层时：搜索要么极慢，要么只能搜最近一小段，要么完全依赖服务端（无网即不可用）。微信要的是**本机、离线、海量历史也能搜**，所以单独养 `*_fts.db`。

## 五、和 SuIM 对照

### 5.1 存储职责不同

| 维度 | 微信本地 FTS | SuIM 现状 |
| --- | --- | --- |
| 层级 | 客户端本地索引 | 服务端权威在 MySQL；SDK 可有本地库，但无对等消息 FTS 服务 |
| 消息主存 | `message_N.db` 会话表 | `msg` 表，主键 `(conversation_id, seq)` |
| 搜索 | 独立 `message_fts` 等 | **基本没有**消息全文检索 |
| 联系人搜索 | `contact_fts` | user 侧偏 ID / 有限字段查询 |
| 同步模型 | 本地写双份（正文 + 索引） | 同步靠 seq / version；搜索需另建 |

SuIM 的 `(conversation_id, seq)` 擅长：**有序、补洞、多端同步**。  
它不擅长：**「给我所有包含某句话的消息」**——那是另一条索引链路的事。

### 5.2 若要对齐体验：两条路

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **端上 SQLite FTS**（学微信） | 离线可搜、不打服务端、隐私好 | 每端自建索引；多端索引一致性；中文分词要自研或引入库；写入放大 |
| **服务端 ES / Meilisearch 等** | 一端建好、多端共享；易做跨设备统一结果 | 要同步管道；延迟与一致性；成本与运维；离线不可用 |

常见产品组合：

- 移动端 / 桌面端：本地 FTS 保「打开就能搜」；
- 服务端：ES 保「换机、Web、运营检索」；
- 主消息表**永远**不背全文检索的锅，只提供权威原文与 seq。

### 5.3 对 SuIM 的直接启示

1. **不要**指望在 `msg` 上加 `LIKE` 或给 `content` 建普通 BTree 就当全文搜。
2. 若做搜索，单独建「可搜文本 → (conversation_id, seq / server_msg_id)」索引层，与 conversation / relation 一样当成一等能力。
3. 写入路径要明确：发送成功落库之后，**异步或同事务**更新搜索索引；撤回 / 删除要删索引项（微信侧甚至有针对撤回清理 FTS 条目的专门逻辑）。
4. 中文分词与字段选择（只索引文本？文件名？引用？）是产品决策，不是存储细节。
5. 客户端若走 OpenIM 风格本地库（`LocalChatLog` 等），本地 FTS 可以挂在 SDK 侧，与服务端 ES 不必二选一。

------

## 六、小结

1. **FTS** 用分词 + 倒排索引解决海量文本检索；核心对手是 `LIKE` 全表扫，不是换一种 SQL 写法而已。
2. **SQLite FTS5** 用虚拟表承载倒排；`UNINDEXED` 列挂业务主键；影子表存段与配置；写入产生 segment，需要合并治理。
3. **微信**把搜索做成独立加密库：`message_fts` / `contact_fts` / `favorite_fts`，与正文库分离、可再分区，用自研分词支撑中文；顶部搜索是多路索引聚合。
4. **`message_fts` 体积偏大是正常的**：它是索引，不是附件仓。
5. **SuIM** 已有清晰的消息序与同步模型，但缺「可搜」这一层；要对齐微信体验，必须在端上 FTS、服务端搜索引擎、或两者组合上单独立项——主表继续只做权威存储。
