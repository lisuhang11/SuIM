# JWT 总结与思考

## 一、一句话本质

JWT（JSON Web Token）是一段由服务端签名、客户端保存的字符串。它把「用户是谁、有什么权限、什么时候过期」写进令牌里，再用密钥签名，让服务端能验证：这段信息是不是自己发的、有没有被人改过。

关键认知：

1. **JWT 是签名，不是加密。** 默认任何人都能 Base64 解码看到 payload。
2. **JWT 解决的是信任问题**（是我发的、没被篡改），不是保密问题。
3. **教科书里的 JWT 是无状态的**：服务端不存 session，靠验签。这既是优点，也带来「难即时吊销」的坑。

---

## 二、为什么会有 JWT

**传统 Session：**

```text
客户端 ── cookie: sessionid=abc ──> 服务端 ──查 Redis/内存──> 用户信息
```

状态在服务端。多机要共享 session，跨域和移动端/第三方调用也不方便。

**JWT：**

```text
客户端 ── Authorization: Bearer eyJ... ──> 服务端 ──验签（计算）──> 用户信息
```

纯 JWT 场景下，服务端不必存会话，水平扩容时共享密钥即可，适合 API 网关和微服务。

> 注意：SuIM **没有**走「纯无状态 JWT」。它用 JWT 做可校验凭证，同时用 MySQL/Redis 管会话生命周期。这是后文重点。

---

## 三、结构：三段，用 `.` 连接

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMifQ.签名...
        Header                          Payload              Signature
```

三段都是 Base64URL（`+`→`-`，`/`→`_`，去掉末尾 `=`）。

### 1. Header

```json
{ "alg": "HS256", "typ": "JWT" }
```

- `alg`：签名算法，安全上最关键
- 还可放 `kid`，做密钥轮换

### 2. Payload

标准声明常见有：`iss`、`sub`、`aud`、`exp`、`nbf`、`iat`、`jti`。  
还可加自定义字段（如 `role`）。

**Payload 只是编码不是加密。** 不要放密码、证件号、密钥等敏感信息。要加密得用 JWE，是另一套东西。

### 3. Signature（HS256 示意）

```text
signing_input = base64url(header) + "." + base64url(payload)
signature     = base64url( HMAC_SHA256(signing_input, secret) )
```

改 header 或 payload，签名必然对不上。

| 算法 | 类型 | 特点 |
| --- | --- | --- |
| HS256/384/512 | 对称 | 同一 secret 签和验；简单，但持有 secret 的都能伪造 |
| RS256 / ES256 等 | 非对称 | 私钥签、公钥验；适合多方验签 |
| none | 无签名 | 生产必须禁用 |

单体内部服务用 HS256 通常够用；开放给第三方验签时再考虑非对称。

---

## 四、完整流程（通识）

**签发：** 校验身份 → 组装 claims → 签名 → 交给客户端。

**验证：** 取出 token → 算法白名单 → 重算签名比对 → 校验 `exp`/`nbf`/`iss`/`aud` → 才信任 payload。

**核心：验签通过之前，payload 里任何内容都不可信。**

---

## 五、安全陷阱清单

1. **`alg: none`**：令牌自称不签名，弱实现会放行。→ 服务端写死算法白名单。
2. **算法混淆（RS→HS）**：用公钥当 HMAC 密钥伪造。→ 同样固定算法。
3. **不校验 `exp`**：库不一定自动查。→ 显式校验，可加几秒 leeway。
4. **敏感信息进 payload**：明文可见。
5. **无法主动吊销**：纯 JWT 的结构性弱点。缓解：短 access + 服务端 refresh、jti 黑名单、token 版本号等——**都会重新引入状态**。
6. **存在 localStorage**：易被 XSS 偷。相对更稳：HttpOnly Cookie（再防 CSRF）。
7. **payload 塞太大**：每请求带宽与解析成本上升。
8. **时钟漂移**：`nbf`/`exp` 误杀。→ NTP 或 leeway。

---

## 六、什么时候不该用「纯 JWT」

| 场景 | 建议 |
| --- | --- |
| 要即时踢人、改密全局下线、单点登录互踢 | 纯 JWT 不擅长，需要服务端状态 |
| 传统服务端渲染、小集群 | Session + Redis 往往更简单 |
| 服务间调用、短命授权、开放 API | JWT 很合适 |

一句话：更怕「状态复杂度」还是更怕「无法即时吊销」？前者偏纯 JWT，后者偏 Session 或混合方案。

---

## 七、落地组合拳（通识）

- 双 token：短 access + 可吊销 refresh  
- 算法白名单，禁用 none  
- 校验 exp/nbf/iss/aud，带 leeway  
- payload 只放非敏感必要字段  
- 全程 HTTPS  
- 紧急吊销用 jti 黑名单或会话表  
- 密钥轮换用 kid  

---

# SuIM 中的 JWT

前面讲的是通识。下面对照 SuIM 真实做法：它用的是 **「JWT 凭证 + 服务端会话」混合模型**，专门补上「纯 JWT 难吊销」这块短板。

## 1. SuIM 里有两类「叫 JWT 的东西」

| 种类 | 用途 | 谁签发 | 有效期量级 | 是否管登录会话 |
| --- | --- | --- | --- | --- |
| **用户登录 JWT** | 标识已登录用户与平台 | user 服务 | 默认约 30 天（可配） | 是，核心会话 |
| **LiveKit 进房 JWT** | 音视频进房授权 | third / livekit 封装 | 约 10 分钟 | 否，房间权限票 |

下文若无特别说明，说的都是 **用户登录 JWT**。LiveKit token 只是同形态的短命授权，和账号会话不是一套生命周期。

---

## 2. 用户登录 JWT：载荷里有什么

签发在 `services/user/internal/token`，算法固定 **HS256**。

自定义字段：

| 字段 | JSON | 含义 |
| --- | --- | --- |
| 用户 ID | `uid` | 当前用户 |
| 平台 ID | `pid` | 客户端平台；必须 > 0 |
| 令牌类型 | `typ` | 固定为 `token` |

标准声明还会带：

- `jti`：令牌唯一 ID  
- `sub`：同样是用户 ID  
- `iat` / `exp`：签发与过期时间  

配置：

```yaml
jwt:
  secret: "..."           # 对称密钥，必填
  expireSeconds: 2592000  # 默认 30 天
```

**设计取舍：** 有效期很长，并不靠「很快过期」来处理退出/改密/顶号，而是靠服务端会话记录主动作废。长 TTL 换来少打扰用户；安全性依赖「验签 + 查会话是否仍有效」。

---

## 3. 签发与解析：代码层边界

| 能力 | 行为 |
| --- | --- |
| `Sign` | 写入 uid/pid/typ + jti/sub/iat/exp，HS256 签名 |
| `Parse` | 验签 + 校验声明（含过期）；`WithValidMethods` 只允许 HS256 |
| `ParseIgnoreExpiry` | 仍验签与完整性，但**允许已过期**；专供退出登录 |
| `Hash` | 对原文做 SHA-256 hex，作为存储与缓存主键 |

安全点对齐通识：

- 算法白名单，不信任令牌自报算法 → 挡住 `none` / 算法混淆一类问题  
- Claims 不完整（缺 uid、jti、typ、pid）直接判无效  
- **logout 允许过期 token**：客户端本地态过期后仍能清掉服务端会话  

---

## 4. 核心设计：JWT 只是门票，会话表才是门禁

纯 JWT：验签过期即可信任。  
SuIM：**验签只是第一步**，还必须在会话存储里查到「这张票还有效」。

### 4.1 登录成功时发生什么

1. 生成令牌 ID，签发 JWT 原文  
2. 计算 `token_hash`  
3. `StartSession`：在同一事务里  
   - 作废该用户在该 `platform_id` 上所有旧会话  
   - 插入新 `auth_tokens` 行（原文 + 哈希 + 过期时间等）  
4. Redis 写入新会话快照；删掉旧快照，并对旧哈希写入 deny  
5. 进程内令牌缓存失效广播，其它 user 实例丢掉旧缓存  

**产品结果：同一账号、同一平台，同时只保留一个有效登录。** 不同平台互不踢。

### 4.2 每次鉴权时发生什么（`ValidateToken` / `loadUsable`）

```text
原始 JWT
  │
  ├─1─ HS256 验签 + typ 检查
  │
  ├─2─ hash = SHA256(原文)
  │      │
  │      ├─ 本地缓存
  │      ├─ Redis 快照 / deny
  │      └─ 未命中再查 MySQL，并回填
  │
  ├─3─ 会话必须：未撤销、用户/平台/类型与 claims 一致、未过期
  │
  └─4─ 用户仍存在且未停用
         → 才算有效登录
```

因此：**伪造一个签名正确但从未入库的 JWT，过不了鉴权**；已被登出/顶号/改密作废的 JWT，即使没到 `exp`，也过不了。

### 4.3 网关怎么用

API Gateway 从 `Authorization: Bearer <token>` 取串，调 user 的 `ValidateToken`。  
通过后把用户 ID 放进请求上下文；需要把 token 传给下游时，用请求头覆盖 body，防止客户端伪造别人的 token。

---

## 5. 存储与缓存分层

| 层 | 存什么 | 作用 |
| --- | --- | --- |
| MySQL `auth_tokens` | 原文、哈希、用户、平台、类型、过期、是否撤销 | 权威会话源 |
| Redis `suim:token:{hash}` | 会话快照（不含原文） | 热路径加速 Lookup |
| Redis `suim:token:deny:{hash}` | 吊销标记，TTL 到原过期时间 | 吊销后即使快照残留也能快速判废 |
| 进程内 localCache | 按 hash 缓存 Lookup 结果 | 降 MySQL/Redis 压力 |
| Redis Pub/Sub `suim:user:token:delete` | 作废的 hash 列表 | 多实例本地缓存一致性 |

Lookup 大致顺序：deny → 快照 → MySQL；命中已撤销也会反映到结果里，上层统一当无效令牌处理。

---

## 6. 哪些操作会让 JWT「提前死亡」

| 操作 | 范围 | 说明 |
| --- | --- | --- |
| 再次登录 / 手机号注册签发会话 | 同用户同平台 | 旧票全废，只留新票 |
| 退出登录 | 同用户同平台 | 过期票也能用来退出 |
| 替换同平台会话 | 同平台除当前外 | 保留本票，清其它 |
| 修改密码 | 该用户全部平台 | 全部重新登录 |
| 账号停用 | 该用户全部平台 | 旧票全废 |
| 注销账号 | 该用户全部 | 删用户并清令牌 |

对应实现都会：DB 标记撤销（或删除）→ 清 Redis 快照 + 写 deny → `invalidate` 推本地缓存删除。

这正是通识第五节说的「黑名单 / 会话表」路线：SuIM 选的是 **白名单式会话表**（有效会话在库里），吊销时再辅以 deny，而不是「签发后直到过期都认」。

---

## 7. 和「纯 JWT 最佳实践」的对照

| 通识建议 | SuIM 实际 | 评价 |
| --- | --- | --- |
| 短 access（15 分钟）+ refresh | 单 token，默认约 30 天 | 用服务端会话换长有效期；没有 refresh 双令牌 |
| jti 黑名单 | 有 jti，但主路径是整行会话 + hash 查找 | 吊销粒度是「会话记录」，不是只记 jti |
| 无状态水平扩展 | 有状态：依赖 MySQL/Redis | 换来即时踢人、顶号、改密全局下线 |
| payload 少放敏感信息 | 只有 uid/pid/typ + 标准时间字段 | 符合 |
| 算法固定 HS256 | 是 | 符合内部服务场景 |
| 过期即失效 | 过期必失效；未过期也可能已被吊销 | 比纯 JWT 更严 |

**一句话总结 SuIM 的立场：**

> JWT 负责「这串字是不是我签的、声称的是谁」；  
> 会话存储负责「这张票现在还准不准用」。  
> 两者缺一不可。

这也解释了为什么可以敢用 30 天 TTL：真正的安全边界不在过期时间，而在「每次鉴权都核对会话是否仍 live」。

---

## 8. LiveKit JWT（对照，避免混淆）

`pkg/livekit` 里手写 HS256，给 LiveKit 进房用：

- `iss` = API Key，`sub` = 用户 identity  
- `exp` 约 10 分钟，带短暂 `nbf`  
- payload 里是房间与发布权限（麦克风/摄像头等）  

它和用户登录 JWT **密钥不同、用途不同、生命周期不同**。客户端进房拿短票；账号登录拿长票。不要混成一套「全局 JWT」。

---

## 9. 思考与可改进点

**已经做得对的：**

1. 正视吊销问题，没有假装纯无状态能搞定 IM 顶号/改密。  
2. 验签算法写死，claim 完整性检查到位。  
3. 用 hash 当索引，避免按超长 JWT 原文查库。  
4. 快照 + deny + 本地缓存失效，在正确性与性能之间有完整链路。  
5. 登出容忍过期 token，贴近客户端真实体验。

**仍可继续想的：**

1. **长 TTL 丢端风险**：设备丢失后，若用户不改密、不登出，票在过期前仍可能被利用——可考虑「活跃续期」、异常设备踢下线，或敏感操作二次验证。  
2. **尚无 refresh 轮换**：单长票被盗即等于长期凭证；双 token 能缩小暴露窗口，但会增复杂度。  
3. **跨服务踢连接**：会话作废后，msggateway 侧在线连接是否瞬时断开，代码里仍有「尚未接入」的缺口；会话无效 ≠ 长连接立刻断。  
4. **密钥轮换**：当前单 `secret`，无 `kid`；轮换时需停机或双密钥过渡。  
5. **MySQL 仍存 token 原文**：便于排查，但库泄露面更大；若只存 hash，需确认没有业务依赖原文回放。

---

## 10. 收束

通识里 JWT 最大的坑是「签出去就难收回」。  
SuIM 的答卷不是回避 JWT，而是：

**用 JWT 做便携、可验签的凭证形态；用会话表 + Redis 做可吊销的真相来源。**

读 SuIM 的 JWT，不要只看 `Sign`/`Parse`；要把 `StartSession`、`Lookup`、`Revoke*`、deny/snapshot、网关 `ValidateToken` 整条链看成一个认证系统。那才是项目里 JWT 真正的样子。
