# etcd 与 Redis 实现分布式锁的优劣对比

## 一、结论先行

| 诉求                                            | 推荐方案                       |
| ----------------------------------------------- | ------------------------------ |
| 强一致、不能出现"两个客户端同时认为自己持锁"    | **etcd**                       |
| 高吞吐、低延迟、锁失效可容忍（幂等 + 业务兜底） | **Redis**                      |
| 已有 K8s / 服务注册发现体系                     | etcd（复用现成集群）           |
| 已有缓存体系、追求开发效率与生态                | Redis（Redisson 等成熟客户端） |

一句话：**etcd 换的是"正确性"，Redis 换的是"性能与便利"。**

------

## 二、两者的实现原理

### 2.1 Redis 分布式锁

**基础版：`SET key value NX PX ttl`**

```redis
SET lock:order:1001 <uuid>:<threadId> NX PX 30000
```

- `NX`：不存在才写入，保证互斥。
- `PX`：设置过期时间，防止持锁进程宕机导致死锁。
- `value` 存唯一标识：释放时校验身份，避免误删别人的锁。

**释放必须用 Lua 保证原子性：**

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**进阶：看门狗（Watch Dog）续期**

Redisson 默认 30s 锁租期，后台每 10s 检查一次，业务未结束则续期，避免"业务没跑完锁先过期"。

**进阶：RedLock（多节点多数派）**

向 N 个**互相独立**的 Redis master 依次加锁，在超过半数节点加锁成功、且总耗时小于锁有效期时，才认为加锁成功。用于缓解单点主从切换丢锁问题。

### 2.2 etcd 分布式锁

**基础版：`Txn` + `Lease` + `Revision`**

```go
// 1. 创建租约
lease := clientv3.NewLease(cli)
leaseResp, _ := lease.Grant(ctx, 10) // 10s TTL

// 2. 事务：仅当 key 不存在时写入，并把 key 绑定到租约
txn := cli.Txn(ctx).
    If(clientv3.Compare(clientv3.CreateRevision("lock/x"), "=", 0)).
    Then(clientv3.OpPut("lock/x", ownerID, clientv3.WithLease(leaseResp.ID))).
    Else(clientv3.OpGet("lock/x"))
```

**排队等锁（官方 `concurrency` 包做法）：**

1. 每个客户端在锁前缀下创建**自己的唯一 key**（如 `lock/x/<uuid>`），全部带上同一个 Lease。
2. 读取该前缀下所有 key，按 `CreateRevision` 排序。
3. 如果自己不是最小 revision，就 **Watch 前一个 key**；前一个 key 被删除时收到事件，再判断自己是否变成最小。
4. 成为最小 revision 即持锁。

**保活：** `Lease.KeepAlive()` 持续续租（默认 TTL/3 一次心跳）。客户端崩溃或网络长时间断开，Lease 到期，其名下所有 key 自动删除，锁自然释放。

**关键点：`concurrency` 包基于 etcd 的 Lease + Revision 机制，天然提供了**"公平排队 + 自动释放 + 前驱唤醒"，不需要自己写轮询。

## 三、核心差异对比

| 维度                       | Redis                                                        | etcd                                                         |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **一致性协议**             | 异步主从复制（默认）；无强一致保证                           | Raft，写入需多数派确认                                       |
| **一致性模型**             | 最终一致                                                     | 线性一致（Linearizable）                                     |
| **主从切换时锁是否可能丢** | **可能丢**：master 加锁成功但未同步到 slave 就宕机，slave 升主后锁消失，另一个客户端可再次加锁成功 | **不会因切换丢失**：只有多数派已提交的写入才会对外可见，未提交的写入不会成为新 leader 的数据 |
| **锁的自动释放**           | TTL 过期删除                                                 | Lease 过期删除（语义等价，但由 Raft 集群统一裁决）           |
| **等待锁的方式**           | 客户端自旋/轮询，或用 pub/sub、Redisson 的信号量             | **Watch 前驱 key**，事件驱动，无空轮询                       |
| **公平性**                 | 默认非公平（抢锁靠运气）；Redisson 提供 `FairLock`           | 天然按 `CreateRevision` 排序，**FIFO 公平**                  |
| **可重入**                 | 需要自己实现（Redisson 用 Hash 结构存 `uuid:threadId` + 计数） | 需要自己实现（同一 owner 判断 + 计数）                       |
| **吞吐 / 延迟**            | **高**：单机 10w+ QPS，亚毫秒级                              | **较低**：每次写入走 Raft 多数派，典型延迟 2~10ms，QPS 万级  |
| **运维复杂度**             | 低（单机/哨兵/Cluster 都很成熟）                             | 中（需 3/5 节点奇数集群，关注磁盘 fsync 延迟、心跳超时）     |
| **对磁盘/网络抖动敏感度**  | 相对不敏感                                                   | **敏感**：磁盘 fsync 慢会导致 Lease 续租失败、leader 选举抖动 |
| **生态与客户端**           | 极丰富（Redisson、RedLock 各语言实现）                       | 官方 `clientv3/concurrency`，Go 生态最佳；Java/Python 有封装但没那么顺手 |
| **附加能力**               | 缓存、限流、计数、排行榜一把梭                               | 配置中心、服务发现、leader 选举、分布式协调                  |
| **典型适用规模**           | 海量、高频、短临界区                                         | 中低频、长临界区、强协调语义                                 |

## 四、各自的优势与劣势

### 4.1 Redis

**优势**

1. **性能碾压**：内存操作 + 单线程命令串行，加解锁开销极低，适合高频短任务（如秒杀扣库存前的串行化）。
2. **生态成熟**：Redisson 把可重入、公平锁、看门狗续期、读写锁、联锁全封装好了，几行代码可用。
3. **一鱼多吃**：大多数团队本来就有 Redis，不用为锁单独引入一套中间件。
4. **部署运维门槛低**：哨兵 / Cluster 方案资料极其丰富。

**劣势**

1. **异步复制导致丢锁**（最致命）：主从切换窗口内，锁可能"人间蒸发"，出现两个客户端同时持锁。
2. **RedLock 有争议且成本高**：需要 5 个独立 master（不能用 Cluster 的分片，因为要保证故障域独立），部署复杂；Martin Kleppmann 与 antirez 的著名论战指出：**RedLock 依赖系统时钟，GC 停顿 / NTP 跳变 / 时钟漂移仍可能破坏安全性**，且它没有 fencing token，无法从根本上防止"过期持锁者继续写数据"。
3. **无原生 fencing token**：需要业务自己保证"旧持锁者的写入被拒绝"。
4. **过期时间是拍脑袋定的**：太短则业务没跑完锁先丢，太长则故障恢复慢；看门狗能缓解但引入了新的复杂度（客户端进程假死时看门狗还在续期）。
5. **等待锁靠轮询**：大量客户端抢同一把锁时，会产生明显的无效请求压力（Redisson 用 pub/sub 优化，但仍有惊群与延迟）。

### 4.2 etcd

**优势**

1. **强一致，不丢锁**：Raft 多数派提交 + Lease 由集群统一管理，主从切换不会让已提交的锁凭空消失。这是它相对 Redis 最本质的优势。
2. **原生事件驱动排队**：Watch 前驱 key，无轮询开销、无惊群，天然 FIFO 公平。
3. **Lease 机制优雅**：一个 Lease 可以绑定多个 key，客户端崩溃即全部释放，语义干净。
4. **可拿到 Revision 作为天然 fencing token**：`CreateRevision` 单调递增，可传给下游存储做"版本校验"，从根本上防御"过期持锁者写入"这一分布式锁的经典难题——**这是 Redis 方案需要额外造轮子才能做到的**。
5. **顺带解决 leader 选举、配置分发、服务发现**：K8s 体系里已经是标配组件。

**劣势**

1. **吞吐低、延迟高**：每次写入都要走一轮 Raft 日志复制 + fsync，QPS 与 Redis 差一个数量级，不适合极高并发抢锁。
2. **对基础设施敏感**：磁盘 IO 慢（尤其机械盘或共享云盘）会导致 `apply request took too long`、心跳超时、频繁选举，进而 Lease 大面积失效、锁集体释放。
3. **不能水平扩展**：Raft 集群节点数增加反而写性能下降，通常固定 3 或 5 节点，写压力有上限。
4. **生态偏弱**：Java / Python 客户端的锁封装不如 Redisson 好用，可重入、读写锁往往要自己写。
5. **误用成本高**：Lease TTL、KeepAlive 频率、时钟同步都要调好，否则会出现"锁频繁自动释放"的诡异问题。
6. **运维知识门槛**：需要理解 Raft、revision、compaction、defrag，出问题时排查链路更长。

## 五、两个都必须正视的根本性问题

无论选哪个，**基于 TTL/Lease 的分布式锁都不是绝对安全的**：

```
客户端 A 获得锁（TTL 30s）
   ↓
A 发生长时间 GC / 网络分区 / 进程被调度挂起 35s
   ↓
锁过期，客户端 B 获得同一把锁
   ↓
A 恢复，它以为自己还持锁，继续写数据库
   ↓
数据被 A、B 交叉写坏  ← 一致性被破坏
```

**根治手段：Fencing Token（栅栏令牌）**

- 每次成功加锁，都拿到一个**单调递增**的编号 token。
- 把 token 一起带给下游存储（DB / 文件系统）。
- 下游拒绝所有 token 小于"已见过的最大 token"的请求。

|           | 获取 fencing token 的难度                                    |
| --------- | ------------------------------------------------------------ |
| **etcd**  | 简单：直接用 `CreateRevision` 或 `ModRevision`               |
| **Redis** | 麻烦：单实例可用 `INCR` 生成，但 RedLock 多节点场景下**没有全局单调计数**，需要额外引入一个计数服务，反而破坏了 RedLock 的"去中心化"初衷 |

这也是 Kleppmann 那篇《How to do distributed locking》的核心论点：**如果锁是为了"正确性"，就必须有 fencing token；如果只是为了"效率"（避免重复计算），那 Redis 锁完全够用。**

## 六、选型决策清单

**选 Redis，如果：**

- 临界区很短、抢锁 QPS 很高（万级以上）。
- 锁失效的后果是"多做一次重复计算"，而不是"数据写坏"。
- 业务本身有幂等设计或数据库唯一约束兜底。
- 团队没有 etcd 运维经验，也不想为此引入新组件。
- 已有 Redisson 生态。

**选 etcd，如果：**

- 锁保护的是**不可重复执行**的操作（扣款、发货、DDL、任务调度唯一执行者）。
- 需要**严格互斥**，不能接受主从切换期间的双主写入。
- 需要**公平排队**和**事件驱动唤醒**，讨厌轮询。
- 需要 **fencing token** 做纵深防御。
- 已经在用 K8s / 有 etcd 集群，边际成本近乎为零。
- 抢锁频率不高（每秒几百到几千次以内）。

**都不选，考虑其他方案：**

- **ZooKeeper**：临时顺序节点 + Watch，语义与 etcd 极其相似，Java 生态（Curator）成熟度更高，老系统常用。
- **数据库乐观锁 / 唯一索引**：并发不高时，`INSERT ... ON DUPLICATE` 或 `UPDATE ... WHERE version = ?` 最简单可靠，没有额外中间件。
- **数据库悲观锁 `SELECT ... FOR UPDATE`**：短事务场景够用。
- **单点串行化**：把并发请求收敛到一个单线程消费者（如 MQ 按 key 分区），从根本上消除对分布式锁的需求。

------

## 七、实践建议（无论选哪个）

1. **锁的 value 必须带唯一标识**（UUID + 线程 ID），释放前校验，防止误删他人锁。
2. **释放锁必须原子**：Redis 用 Lua，etcd 用 `Txn` + `Compare(value)`。
3. **TTL 要大于业务最长耗时**，并配合自动续期；同时给续期设上限，避免客户端假死导致锁永久占用。
4. **加锁要有超时和重试上限**，不要无限阻塞把线程池打满。
5. **临界区内不要做慢 IO**（远程调用、大批量数据库操作），锁粒度越小越好。
6. **可重入计数要在同一把锁内维护**，且释放时逐层递减到 0 才真正删 key。
7. **监控三件事**：加锁失败率、持锁时长分布、锁自动过期次数（异常升高说明 TTL 或续期有问题）。
8. **关键路径加 fencing token 或数据库层校验**，把分布式锁当"性能优化"而非"正确性保证"。
