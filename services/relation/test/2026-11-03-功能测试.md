# 2026-11-03 relation 功能测试

## 目标

确认好友关系在四条边界上的当前行为，再决定要不要改实现。

- 只删除一侧之后，另一侧的好友还在，删除的一侧可以再次申请，同意后两边恢复。
- 同一对用户只有一条申请。拒绝或双方都删掉好友之后再申请，会盖掉原来的留言和处理结果。待处理的申请不能再发一次。
- 好友刚好 20 个时默认一页装完。第 21 个出现在第二页。置顶的人排在第一页第一条。
- 拉黑不删掉还留着的好友行。被拉黑时同意申请失败，申请保持待处理。解除拉黑后可以同意。

## 范围

relation 服务自己的逻辑，连开发库里的 MySQL。用户是否存在由测试里的名单代替，不写 `user` 表。不测消息服务，也不做性能和压测。

已有用例继续覆盖申请、同意、拒绝、拉黑、备注、增量同步和两个人的分页。这次新增的用例在 `server_func_test.go`。

## 用例

| 用例 | 要确认的结果 |
| --- | --- |
| `TestOneSidedDeleteThenReapply` | A 删除 B 后，A 的列表为空，B 的列表仍有 A。A 可以再次申请。待处理时再发一次被拒绝。B 同意后两边都是好友。两侧版本明细都是插入。 |
| `TestRequestReopenOverwrites` | 拒绝后再申请，同一行变回待处理，留言换成新的，处理留言和处理时间被清空。待处理时再发不改留言。双方都删除后再申请，原先已同意的那一行同样被打开，仍然只有一行。 |
| `TestFriendPageBoundary` | 20 个好友时默认页 20 条，偏移 20 为空。21 个好友时两页分别是 20 和 1，合起来不丢不重。把最后一个人置顶后，他出现在第一页第一条，不在第二页。 |
| `TestBlockKeepsFriendAndHoldsAgree` | A 删掉自己这边后再次申请，再拉黑 B。B 这边的好友行还在。同意返回拉黑错误，申请仍是待处理。解除拉黑后同意成功，两边恢复好友。 |

## 结果

2026-11-03 跑过。四条新用例都通过，整包 `go test ./services/relation/ -count=1` 也通过。

| 用例 | 结果 | 观察到的行为 |
| --- | --- | --- |
| `TestOneSidedDeleteThenReapply` | 通过，0.14s | 只删一侧后，对方列表里这个人还在。删除方可以再次申请，重复的待处理申请会被拒绝。同意后两边恢复。两边的版本明细都写成插入，包括本来没删掉的那一侧。 |
| `TestRequestReopenOverwrites` | 通过，0.09s | 拒绝后再申请，还是同一行，留言换成新的，处理留言和时间被清空。待处理时再发一次不改原留言。双方都删除后再申请，已同意的那一行同样被打开，库里仍然只有一行。 |
| `TestFriendPageBoundary` | 通过，0.56s | 20 个好友占满默认一页，再偏移就没有了。21 个好友分成 20 和 1，合起来不丢不重。置顶的人在第一页第一条，不在第二页。 |
| `TestBlockKeepsFriendAndHoldsAgree` | 通过，0.09s | 拉黑没有删掉对方还留着的好友行。这时同意申请失败，申请继续待处理。解除拉黑后再同意，两边都是好友。 |

这四条记录的是现在的行为，不是待修项。单边删除后对方仍保留好友、以及重新同意时没删掉的那一侧也记成插入版本，都按当前实现断言。
