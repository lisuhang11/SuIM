跨域是前端最高频的坑之一，下面按「是什么 → 为什么 → 怎么解决 → 怎么排查」四层讲清楚。

## 一、先搞懂「源」（Origin）

**源 = 协议 + 域名 + 端口**，三者完全一致才叫同源。注意：**路径不算源的一部分**。

假设当前页面在 `http://www.a.com:8080`：

| 请求地址                         | 是否跨域 | 原因                         |
| -------------------------------- | -------- | ---------------------------- |
| `http://www.a.com:8080/api/user` | 同源     | 只有路径不同，路径不参与判断 |
| `http://www.a.com/api/user`      | 跨域     | 端口不同（8080 → 80）        |
| `https://www.a.com:8080/api`     | 跨域     | 协议不同（http → https）     |
| `http://api.a.com/api`           | 跨域     | 子域名不同                   |
| `http://a.com/api`               | 跨域     | 有无 www 也算不同域名        |

补充一点：`http://a.com` 和 `http://a.com:80` 是同源的，因为 80 是 http 的默认端口，会被省略。

## 二、为什么浏览器要拦你

这套规则叫**同源策略（Same-Origin Policy）**，本质是安全隔离。

想象一下没有它会怎样：你登录了网银，Cookie 还在。然后你打开了一个恶意网页，它的 JS 直接 `fetch('https://bank.com/api/transfer')`——因为浏览器会自动带上你在 bank.com 的 Cookie，这个请求就是「已登录状态」的，钱可能就没了。同源策略就是防这个的。

这里有两个**最关键的认知**，很多人误解了一辈子：

### 1. 限制的是浏览器，不是服务器

- 你用 Postman、curl 调任何接口都不会跨域——它们不是浏览器，没这个策略。
- 服务器 A 调服务器 B 也不会跨域。
- 所以「跨域」是浏览器单方面的行为，**必须由后端配合返回许可头，或者用代理绕开浏览器**。前端自己改改代码是解决不了的（JSONP 那种除外）。

### 2. 跨域报错 ≠ 请求没发出去

对于简单请求，请求**已经到达服务器并且被处理了**，服务器也返回了数据。只是浏览器一看响应头里没有 `Access-Control-Allow-Origin`，就把响应**扣下来不给你的 JS 读**，然后在控制台报错。

> 这个区别很重要：如果你的接口是「转账」「扣库存」这种有副作用的写操作，跨域失败时**后端其实已经执行成功了**，只是前端拿不到结果。这也是一类经典线上事故的来源。

## 三、简单请求 vs 预检请求

浏览器把跨域请求分成两类，处理方式完全不同。

**满足以下全部条件 = 简单请求（直接发）：**

- 方法是 `GET`、`HEAD` 或 `POST`
- `Content-Type` 只能是这三种之一：`application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`
- 没有自定义请求头（只带浏览器安全名单里的头，如 `Accept`、`Accept-Language`）

**只要有一条不满足 = 非简单请求（先发预检）。**

最典型的触发场景：你发 JSON（`Content-Type: application/json`），或者加了 `Authorization: Bearer xxx`。

这时浏览器会**先自动发一个 `OPTIONS` 请求**去问服务器：

```http
OPTIONS /api/user HTTP/1.1
Origin: http://www.a.com:8080
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

服务器回答「可以，我允许这个源、这些方法、这些头」，浏览器才发真正的请求。这就解释了很多人的困惑：**我明明只调了一次接口，Network 面板里怎么有两条？**——第一条就是预检。

预检结果可以被缓存（`Access-Control-Max-Age`），避免每次都多一次往返。

## 四、解决方案

### 方案 1：CORS（主流做法，生产环境用这个）

后端在响应头里明确授权。核心是这几个头：

| 响应头                             | 作用                             |
| ---------------------------------- | -------------------------------- |
| `Access-Control-Allow-Origin`      | 允许哪个源访问                   |
| `Access-Control-Allow-Methods`     | 允许哪些方法                     |
| `Access-Control-Allow-Headers`     | 允许哪些自定义请求头             |
| `Access-Control-Allow-Credentials` | 是否允许带 Cookie                |
| `Access-Control-Max-Age`           | 预检结果缓存多久（秒）           |
| `Access-Control-Expose-Headers`    | 允许前端 JS 读取哪些自定义响应头 |

**Express：**

```javascript
const cors = require('cors');
app.use(cors({
  origin: 'http://www.a.com:8080',  // 生产环境别写 '*'
  credentials: true,                 // 需要带 Cookie 时
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'OPTIONS'],
  maxAge: 86400
}));
```

**Nginx：**

```nginx
location /api/ {
    add_header Access-Control-Allow-Origin  $http_origin always;
    add_header Access-Control-Allow-Methods 'GET, POST, PUT, DELETE, OPTIONS' always;
    add_header Access-Control-Allow-Headers 'Content-Type, Authorization' always;
    add_header Access-Control-Allow-Credentials 'true' always;
    add_header Access-Control-Max-Age 86400 always;

    if ($request_method = OPTIONS) {
        return 204;    # 预检直接返回，不转发给后端
    }
    proxy_pass http://backend;
}
```

`always` 这个参数别漏——不加的话，`add_header` 只在 2xx/3xx 响应上生效，接口一报 500 跨域头就没了，你会看到「明明后端出错了，前端却报跨域」这种误导性错误。

**Spring Boot：**

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://www.a.com:8080")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

**前端也要配合**（带 Cookie 的场景）：

```javascript
// fetch
fetch(url, { credentials: 'include' });
// axios
axios.defaults.withCredentials = true;
```

### 方案 2：开发环境代理（本地开发首选）

原理很简单：让浏览器只跟同源的 dev server 说话，由 dev server 在**服务端**转发给真正的后端。服务器之间没有同源策略，问题就消失了。

**Vite：**

```javascript
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://192.168.1.100:3000',
        changeOrigin: true,
        rewrite: path => path.replace(/^\/api/, '')
      }
    }
  }
}
```

**webpack-dev-server：**

```javascript
devServer: {
  proxy: [{
    context: ['/api'],
    target: 'http://192.168.1.100:3000',
    changeOrigin: true
  }]
}
```

前端请求写相对路径 `/api/user` 就行，不要写完整域名。

**生产环境同理**，用 Nginx 做反向代理：把前端静态资源和 API 挂在同一个域名下（`www.a.com` 提供页面，`www.a.com/api` 转发到后端），从根上就没有跨域。这是最省心的部署方式。

### 方案 3：JSONP（了解即可，别用）

利用 `<script>` 标签加载资源不受同源限制的特点：

```html
<script>
function handleData(data) { console.log(data); }
</script>
<script src="http://api.b.com/data?callback=handleData"></script>
```

后端返回 `handleData({...})`，浏览器把它当脚本执行，就调到了你的函数。

局限很明显：**只支持 GET**、需要后端专门配合、有 XSS 风险、没有正常的错误状态码。现在基本只在兼容古董浏览器时才会见到。

### 方案 4：postMessage（跨窗口通信）

用于 iframe、`window.open` 打开的窗口之间传消息，是浏览器官方提供的跨源通信 API：

```javascript
// 父页面
iframe.contentWindow.postMessage({ type: 'init' }, 'http://child.com');

// 子页面
window.addEventListener('message', e => {
  if (e.origin !== 'http://parent.com') return;  // 必须校验来源
  console.log(e.data);
});

```

**一定要校验 `e.origin`**，否则任何页面都能给你发消息。

### 补充：WebSocket 不受同源策略限制

`ws://` / `wss://` 连接可以跨域建立，但服务端应该自己检查 `Origin` 头做白名单，否则会有跨站 WebSocket 劫持风险。

## 五、实战排查清单

遇到跨域报错，按这个顺序看：

1. **`No 'Access-Control-Allow-Origin' header is present`**
   → 后端没配 CORS，或者 Nginx 没加 `always`，或者预检请求被后端路由拦下返回了 404/405。
2. **`The value of the 'Access-Control-Allow-Origin' header ... must not be the wildcard '*' when credentials mode is 'include'`**
   → 带 Cookie 时 `Allow-Origin` 不能用 `*`，必须回具体的源。通常写成动态返回 `$http_origin`（配合白名单校验）。
3. **`contains multiple values '*, *'`**
   → 重复设置了。最常见是 Nginx 加了一遍、后端应用又加了一遍。只保留一处。
4. **预检 OPTIONS 返回了 200，但真实请求 404**
   → 后端只处理了 OPTIONS，没注册实际的方法/路由；或者被网关、鉴权中间件在 OPTIONS 之前就拦掉了（鉴权中间件要放行 OPTIONS）。
5. **本来能通，加了个 header 就跨域了**
   → 你把简单请求变成了预检请求，而后端没配 `Access-Control-Allow-Headers`。
6. **本地好的，上线就跨域**
   → 开发时走的是 dev server 代理，生产环境没有对应的 Nginx 转发配置。检查请求是不是写死了后端的完整域名。
7. **接口 500 却报跨域错误**
   → 后端异常时没返回 CORS 头。这是 `always` 缺失的典型症状，别被误导去查跨域配置，真正的问题是后端挂了。

## 六、总结

> 跨域源于浏览器的同源策略，源由协议、域名、端口三者共同决定，限制的是浏览器而非服务器。CORS 是标准解法：简单请求直接发送但浏览器拦截未授权响应，非简单请求会先发 OPTIONS 预检。开发环境用 dev server 代理、生产环境用 Nginx 反向代理，都能从架构上避开跨域；带 Cookie 时 `Allow-Origin` 必须指定具体源并开启 `Allow-Credentials`。
