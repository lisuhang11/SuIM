## 一句话结论

分库分表本质上是在单机资源（磁盘、IOPS、连接数、写入吞吐）接近极限时，把数据量和访问压力水平切分到多台机器上；但它会把「单机数据库问题」转换成「分布式系统问题」，后者更贵、更难改，所以它是**最后手段，不是首选手段**。

------

## 前提：这套判断只适用于 OLTP

先厘清一个容易混淆的前提。本文讨论的场景是**交易型负载**：高频点查、小范围写入、按主键或少量索引访问。

如果你的瓶颈其实是**多维报表、任意条件筛选、大范围聚合**，那正确解法是数据仓库、ES 或列存，而不是分片——把分析型负载分到更多 MySQL 分片里，只会让问题更糟：每片都要扫一遍再归并，尾延迟被最慢的分片拖着走。

这两类负载的处理顺序完全不同，先分清再往下看。

------

## 一、上分片之前，先吃完更便宜的手段

顺序必须先钉死——否则分片会变成逃避治理的借口。

| 手段                   | 解决什么           | 收益                       | 局限                                                         |
| ---------------------- | ------------------ | -------------------------- | ------------------------------------------------------------ |
| SQL / 索引治理         | 慢查询、全表扫     | 不改架构，当天可上线       | 治不了结构性容量问题                                         |
| 缓存（本地 + Redis）   | 读热点             | 不占数据库资源，命中即返回 | 只加速读；穿透、雪崩、一致性要另做                           |
| 读写分离               | 读多写少           | 读能力近似线性扩展         | 不解决单表体积与写入上限，且引入主从延迟                     |
| 垂直拆分（按业务拆库） | 故障隔离、团队边界 | 跨库面远小于水平分片       | 跨库 JOIN 与分布式事务依然存在                               |
| 冷热归档 / 分区表      | 历史数据、管理便利 | 主表体积骤降，成本直降     | 分区表不解决连接数与单机写上限；MySQL 分区表要求唯一索引必须包含分区键 |
| 大字段垂直拆表         | 行宽、页命中       | 单页容纳行数上升           | 多一次查询，仍单机                                           |

### 这些手段不是互斥选项

上表容易读成「做了缓存就不用分片」，这是一个误解。真实关系是：

- **缓存、读写分离、归档是叠加的**，分片之后依然要做，分片不替代它们；
- **垂直拆库是前置的**，不是替代的——垂直拆完单库还撑不住，仍要在垂直结果上做水平分片，两阶段成本叠加；
- 只有**「换成分布式数据库」和「自研分片中间件」之间**，才是真正的二选一。

### 真正该上水平分库分表的信号

上述手段用完后，同时满足这三条：

1. 单机磁盘、IOPS、连接数、写入吞吐或备份 RTO 有**实测数据**证明顶不住；
2. 增长曲线显示**18 个月内会再次撞墙**（分片方案落地通常要 3～6 个月）；
3. 访问模型能抽出一个**稳定、高基数、覆盖绝大多数请求的分片键**。

第三条最关键。抽不出分片键，说明业务模型还没稳定，此时分片等于把未来的返工成本提前锁定。

## 二、为什么最终还是要分

### 1. 单表数据量的三重衰减

InnoDB 的索引是 B+ 树，行数增长带来三个连锁反应：

**树高上升，随机 IO 增加。** 非叶子节点每页（16KB）能放约 1170 个「主键 + 指针」条目，叶子节点每页能放多少行完全取决于行宽：

| 单行大小 | 每个叶子页行数 | 三层 B+ 树可容纳 |
| -------- | -------------- | ---------------- |
| 约 200 B | 约 80          | 约 1 亿行        |
| 约 1 KB  | 约 16          | 约 2000 万行     |

所以「千万级 3 层、亿级 4 层」只是常见行宽下的经验值，**宽表可能几百万行就到 3 层**。判断依据是行宽与索引大小，不是单纯的行数。

**索引常驻内存的比例下降。** buffer pool 装不下热索引后，查询从「内存寻址」退化为「磁盘随机读」，性能是断崖式的，不是线性的。

**写入维护成本上升。** 二级索引越多，插入时的页分裂与索引更新代价越大，写放大直接吃掉 IOPS 预算。

### 2. 运维成本随体积线性恶化

- **DDL 变慢**：加字段、加索引的耗时与数据量正相关，在线 DDL 的空间占用、主从延迟、锁风险同步上升；
- **备份 / 恢复 / 主从重建**从分钟级变成小时级，直接压缩故障恢复窗口（RTO）；
- **数据迁移、在线校验、误操作回滚**都从「几分钟能搞定」变成「要排窗口」。

### 3. 单机硬上限

| 维度       | 典型瓶颈                                                     |
| ---------- | ------------------------------------------------------------ |
| 连接数     | 默认 `max_connections=151`，可配到几千，但生产环境常在几百到一千就该警惕——每连接的内存缓冲与 mutex 争用成本陡增 |
| 写入       | 单主写入无法水平扩展；并行复制仍受事务依赖与写放大限制，写入高峰期从库会持续积压 |
| CPU / IOPS | 云盘 IOPS 有明确配额，高并发写入通常先撞 IOPS 墙             |
| 锁竞争     | 热点行、热点索引页的锁等待随并发恶化                         |

关于写入瓶颈要说得更准一点：MySQL 5.7 起已有基于组提交的并行复制，8.0 的 WRITESET 进一步降低了冲突判定粒度，「从库回放是纯串行」的说法已经过时。但**同一事务内、同一行上的操作依然串行**，写放大场景下并行度上不去，积压问题仍然存在——只是机理从「复制线程单线程」变成了「事务依赖无法并行」。

### 4. 非性能因素

- **故障隔离**：核心交易与日志混库，一个慢查询拖垮全站；
- **业务隔离与权限**：不同业务线独立库，便于拆团队、独立扩容与回滚；
- **冷热分离**：历史归档，主库只留热数据，成本与性能双赢。

### 5. 一个被低估的做法：先为分片做准备，但现在不分

如果增长曲线表明两年内会撞墙，但当前还没到，最划算的动作不是立刻分片，而是**把分片键写进现在的数据模型**：

- 主键用**全局唯一、趋势递增**的 ID（雪花或号段），不要用数据库自增；
- 在订单、流水这类未来要分片的表上，**冗余一份 `user_id`**，即使现在用不上；
- 所有查询路径**强制带上分片键**，把它变成接口契约而不是可选项。

这样将来真要分片时，只需要改路由层，不需要改数据模型和业务代码。**分片键是不可逆的架构决策**，一旦选定再改，等于全量重刷数据加全量改代码。

## 三、拆分形态与落地方式

### 3.1 四种拆分

| 方式         | 拆什么                 | 解决的问题             | 代价                                     |
| ------------ | ---------------------- | ---------------------- | ---------------------------------------- |
| 垂直分库     | 按业务拆库             | 业务隔离、单库压力     | 跨库 JOIN、分布式事务                    |
| 垂直分表     | 大字段、冷字段拆出     | 单行变窄、页命中率提升 | 多一次查询                               |
| 水平分表     | 同库内按分片键拆多张表 | 单表体积               | 跨表查询、路由                           |
| 水平分库分表 | 跨实例拆               | 容量与并发全维度扩展   | 下述几乎全部问题，加运维复杂度           |
| 分区表       | 单实例内物理分区       | 管理、归档方便         | 不解决连接数与单机上限，**不能替代分库** |

**关键点：分表 ≠ 分库。** 只分表能缓解单表体积，解决不了连接数和单机写入瓶颈；并发真正扛不住时必须分库。

### 3.2 落地形态：四种做法，取舍完全不同

这一层常被跳过，但它决定了后续 80% 的运维负担落在谁身上。

| 形态           | 代表                                  | 侵入性                         | 适合场景                                   |
| -------------- | ------------------------------------- | ------------------------------ | ------------------------------------------ |
| 客户端 SDK     | Sharding-JDBC                         | 嵌在应用里，多语言要各写一套   | 单一 Java 栈、追求极低延迟、能接受升级跟随 |
| 代理层         | ShardingSphere-Proxy、MyCat、ProxySQL | 应用无感，跨语言，天然收敛连接 | 多语言栈、连接数压力大、想要统一入口       |
| 数据库原生分区 | MySQL 分区表                          | 无                             | 只处理单表体积与归档，不解决并发           |
| 分布式数据库   | TiDB、OceanBase、PolarDB-X            | 换引擎                         | 想彻底摆脱分片逻辑，且能承担新引擎运维     |

**这是「最后手段」之外的另一条路。** 自研分片中间件的长期成本不只是开发，更是后面十几年的迁移、扩容、DDL、对账、排障工具链；分布式数据库把这些能力内置，代价是引入新引擎的学习与运维成本、以及部分 MySQL 特性的兼容差异。选哪条，本质是「用人力换可控」还是「用可控换人力」。

### 3.3 初始分片数怎么定

**宁可一次多分，不要按当前数据量刚好够用来分。**

原因很简单：扩分片要搬数据、要双写、要校验、要切流，是全套高风险操作；而分片数偏多只是多几张表，路由成本几乎不变（路由是 O(1) 的计算，不是遍历）。

常见做法是按**三年后的数据量 + 单分片不超过 500 万～1000 万行**倒推，再向上取 2 的幂，方便后续双倍扩容。

## 四、分片之后会多出哪些问题

按性质分三组：**正确性、性能、工程**。前一组出问题是数据错，后两组出问题是能用但难受。

### A. 正确性：数据会错的那一类

#### A1. 分布式事务与一致性

本地事务失效。跨库写入只有两条路：

- **2PC / XA**：性能差，且真正的风险不是「协调者单点不可用」，而是 TM 在提交阶段崩溃后产生 **in-doubt（悬挂）事务**——分支上的锁长时间不释放，只能靠人工或定时任务介入清理；
- **TCC / Saga / 本地消息表 + 最终一致**：业务必须自己承担中间态。

后者的代价是三项硬要求：

- **业务要容忍中间态**：用户可能短暂看到「半成功」，前端如何展示「处理中」必须事先定；
- **每个写路径要幂等**：至少一次投递下，不能重复下单、重复扣款；
- **要有补偿与对账兜底**：补偿不是异常处理，是常态路径的一部分。

原来一句 `BEGIN...COMMIT`，现在往往是一套状态机。**这不只是存储改造，也是产品语义改造。**

#### A2. 跨库 JOIN 没了

- 小表做成**全局表**（每库一份副本），代价是写放大与副本同步延迟；
- 大表只能**字段冗余**，用消息保最终一致——同样是写放大，且失败即长期不一致；
- 或者应用层拼装，两次查询内存 join，数据量大时内存与 RT 都不可控。

冗余不是免费的：**源表一变更，所有副本都得跟着更新**，这是持续的一致性负债。

#### A3. 全局唯一 ID

自增主键在多库下必然冲突。三种方案与各自的坑：

| 方案                | 注意点                                                       |
| ------------------- | ------------------------------------------------------------ |
| 雪花算法            | 依赖时钟，必须防回拨；worker 编号不能撞，容器化部署要重新设计分配方式 |
| 号段模式（如 Leaf） | 依赖 DB 或号段服务的可用性；必须双 buffer 预取，否则号段耗尽会阻塞；多机房要规划号段分配 |
| UUID                | 随机主键导致页分裂与缓冲池污染，作聚簇索引要谨慎             |

还要权衡一件事：**ID 里要不要嵌分片信息**。嵌了路由快，但会暴露数据规模、且绑死分片规则；不嵌则每次查询都要多一次路由计算或查表。

#### A4. 跨分片唯一约束

手机号、订单号、邮箱这类全局唯一字段，数据库保不住。只能靠：唯一路由表、分布式锁加双检、或业务幂等加事后对账。**这不是性能问题，是正确性问题**，一旦漏掉就是脏数据。

#### A5. 异构索引与路由表自身的一致性

为了补非分片键查询，通常要建 `email → user_id`、`order_no → user_id` 这类映射表。新问题随之而来：

- 注册、下单变成「先写路由再写数据」（或反之），失败要补偿；
- 改绑手机、改单号要改两处，顺序与回滚要设计；
- 一旦不一致，表现是「偶发查不到」「登录成功但资料 404」——**极难排查，且无法通过看日志定位**。

这些路由表是新的正确性中心，不是附属配置。它们本身也要有监控、校验和修复工具。

#### A6. 分片键选错 = 每条查询都广播

分片键要高基数、分布均匀，且覆盖绝大多数查询。按 `user_id` 分片后，`WHERE order_no = ?` 无法路由，只能全分片广播，成本随分片数线性上升，**并且这种退化在压测里很难暴露**（数据量小时看不出差别）。

补救手段有三种，各有代价：

- **异构路由表**：多一次查询，多一份一致性负担；
- **基因法**：把 `user_id` 的后几位嵌进 `order_no`，同一用户的订单落同片——但会让 ID 结构暴露，且改分片规则时失效；
- **复杂查询丢搜索引擎**：多一套数据同步链路。

同时必须收紧接口契约：**无分片键的列表与搜索不能再当默认能力**，否则分片从第一天起就名存实亡。

### B. 性能：能用但会难受的那一类

#### B1. 跨分片查询：分页、排序、聚合

`ORDER BY create_time LIMIT 100000, 20` 在分片下最痛：

- 每片都要取数再归并，翻页越深越慢；
- 并行打多片时，**尾延迟等于最慢那一片**，P99 容易被单个慢分片拖垮；
- `COUNT(*)`、`SUM`、`GROUP BY` 要汇总所有分片，片数越多越慢，且**无法走索引下推**。

深分页通常改成**游标分页（seek method）**，或走离线宽表 / ES。在线库不再承担「任意条件运营报表」。

#### B2. 数据倾斜与热点

按用户分片，头部商户、大 V 会打成单片热点；按时间分片，写入永远压在最新分片。

需要二级拆分、热点隔离、限流，或哈希打散。**分片不自动消灭热点，只把「整库热点」变成「单片热点」**——而且单片热点的排查难度更高，因为监控要下沉到分片维度才能看见。

#### B3. 连接数反而可能爆炸

`分片数 × 应用实例数 × 每池连接` 很容易超过 `max_connections`。

这是分库后**最容易漏估**的一点：数据扩容了，连接先把实例打挂。必须重做连接池上限（按分片配额分配，而不是每个分片都配满），或用代理层统一收敛。

#### B4. 主从延迟变成跨片不一致

单库时代，主从延迟只影响「写后读」的个别请求。分片之后，**不同分片的延迟不同**：

- 同一笔业务跨两个分片读，可能读到不同时间点的快照；
- 导出、备份、报表**无法获得全局一致快照**，只能取「各片大致同一时刻」；
- 跨库校验、对账的基准时间点很难对齐。

需要在业务上明确：哪些读必须走主库，哪些可以容忍延迟，以及「全局快照」这件事在分片架构下是否还成立。

#### B5. SQL 能力被削减

这取决于中间件版本，不能一概而论。常见限制集中在：跨库子查询、`UNION`、跨片 `JOIN`、部分函数、`DISTINCT`、窗口函数——**有些是彻底不支持，有些是支持但改写成多片归并、性能极差**。

研发要长期写「分片友好 SQL」，这是持续的心智负担与测试成本，也是最容易被低估的一项。选型时应该拿真实业务 SQL 去做兼容性验证，而不是看文档列表。

### C. 工程：不出错但会拖垮团队的那一类

#### C1. 扩容与数据迁移

先说清楚取模扩容到底多痛：

| 变更                    | 需要搬动的数据 |
| ----------------------- | -------------- |
| `% 4` → `% 5`（加一台） | 约 80%         |
| `% 4` → `% 8`（翻倍）   | 恰好 50%       |

翻倍之所以是「最优取模扩容」，是因为 `h % 4 = (h % 8) % 4`——只有第 3 位为 1 的那一半数据需要动，且刚好精准填满新增的 4 个分片。而「加一台机器」会打乱几乎全部映射。

所以实际方案是：**双倍扩容**、**一致性哈希 + 虚拟节点**（搬动约 1/N）、或**预分槽**（如 Redis Cluster 的 16384 槽、Codis 的 1024 槽，扩容以槽为单位迁移）。

无论哪种，都必须配套：双写、全量加增量迁移、逐片数据校验、灰度切流、可回滚。这是**高风险变更**，不是改配置。**没有迁移方案的分片方案等于半成品。**

#### C2. 多分片 Schema 变更

单库一次 DDL，分片后是 N 次。

- 滚动加字段期间，新旧代码、新旧 Schema 并存，必须保证双向兼容；
- 某片 DDL 失败会造成「同逻辑表结构不一致」，而这种不一致往往几天后才被某条 SQL 触发；
- `gh-ost`、`pt-osc` 这类工具要**按分片调度**，且重试必须幂等，否则会留下临时表和触发器；
- 需要变更编排与版本门禁，以及「先扩列兼容、再切流量、最后清理」的发布纪律。

#### C3. 可观测性与故障放大

- 1 个实例变成几十上百片：监控、告警、慢查询、链路追踪都要按分片维度重建；
- 故障域并没有变小——**节点数量变多了，故障点也就变多了**。分库能隔离业务故障域，但不能减少单节点故障概率；
- 真正的风险是**重试放大**：单节点抖动 + 无预算的盲目重试，会把局部故障放大成全站雪崩，必须配置限流、熔断与重试预算。

#### C4. 备份、校验与对账

- 备份要尽量对齐一致时间点，物理备份需按分片分别执行与验证；
- 跨库对账要单独建设，常用手段是：分片内 `CHECKSUM TABLE` 比对、按时间窗抽样比对、基于 binlog 的逐条回放校验；
- 迁移与修复工具要能**按分片灰度**，否则一次误操作就是全量事故。

#### C5. 测试、发布与故障演练

- 单测不够：要覆盖「路由成功但数据失败」「只写一半」「补偿重入」这些组合；
- 集成环境要多数据源，CI 更重、更慢；
- 灰度要以分片或用户集合为单位，回滚路径要事先演练；
- 混沌演练：单片不可用时，是快速失败，还是拖死整个线程池？

**分片把「存储扩容」变成了「工程组织扩容」。**

## 五、收益与新问题对照

| 单库的痛                   | 分片缓解了吗                   | 换来的新问题                          |
| -------------------------- | ------------------------------ | ------------------------------------- |
| 表太大、DDL / 备份慢       | 是                             | 迁移、多数据源、多分片 DDL 编排       |
| 写打满、IOPS / 连接顶不住  | 通常是（键均匀时）             | 热点片、连接池爆炸、代理层            |
| 故障域过大                 | 部分是：能隔离业务，但节点变多 | 重试放大、可观测性变复杂              |
| 简单唯一约束 / JOIN / 报表 | 否，往往更差                   | 路由表、字段冗余、数仓 / ES、最终一致 |
| 本地事务                   | 否                             | 状态机、幂等、补偿、对账              |
| 全局一致快照               | 否                             | 跨片快照失效、写后读不一致            |
| 运维简单                   | 否                             | 持续人力与工具链投入                  |

## 七、决策顺序

1. **SQL 与索引治理**——往往能拿回大部分性能；
2. **缓存**——挡住读热点；
3. **读写分离**——扩展读能力；
4. **冷热归档**——把历史数据挪走，主表体积骤降；
5. **垂直拆库**——按业务隔离，成本低、收益明确；
6. **换分布式数据库**——不想长期维护分片中间件时选这条；
7. **水平分库分表**——单机写上限与表体积都到顶，且分片键稳定。

前五步是叠加的，六和七是二选一。**如果问题能用「更好的索引 + 更多从库 + 归档」解决，就不要分库分表；如果瓶颈明确落在单机写入和单表体积上，且数据模型已经稳定，再分。**
