# 分库分表的分片算法

分片算法（Sharding Algorithm）解决的核心问题是：**给定一条数据的分片键（如用户 ID、订单 ID），如何计算它应该落在哪个库、哪张表**。选错算法会导致数据倾斜、扩容困难或查询全表扫描。下面按常用程度介绍九类算法。

## 1. 哈希取模

**思路**：对分片键做哈希后对分片数取余。

```
库序号 = hash(user_id) % 库数量
表序号 = hash(user_id) / 库数量 % 表数量
```

**例子**：4 个库，每个库 8 张 `t_order` 表。`user_id = 1001`：

- `hash(1001) % 4 = 1` → 落到 db_1
- `(hash(1001) / 4) % 8 = 6` → 落到 db_1.t_order_6

> **注意**：如果分片键本身分布不均匀（比如自增 ID 有规律、号段集中），建议**先哈希再取模**，不要直接 `id % N`——有规律的 ID 直接取模依然会倾斜。

**优点**：数据分布均匀，实现简单，是最常用的算法。

**缺点**：扩容时模数变化，几乎全部数据都要迁移。缓解办法是**一次规划到位**（如直接分 1024 张逻辑表，物理上先放到少量库，扩容时只搬表不改路由规则）。

## 2. 范围分片

**思路**：按分片键的连续区间划分，每个分片负责一段范围。

**例子**：订单表按 `order_id` 分段，每 1000 万一片：

| 分片 | order_id 范围     |
| ---- | ----------------- |
| db_0 | 1 ~ 1000万        |
| db_1 | 1000万+1 ~ 2000万 |
| db_2 | 2000万+1 ~ 3000万 |

`order_id = 15000003` → 落在 db_1。

**优点**：扩容只需新增一个分片承接新数据，旧数据不动；范围查询高效（查"某段时间的订单"只扫一两个分片）。

**缺点**：**写热点集中在最后一个分片**（新数据永远往最新的片写）。常见于按时间分片的日志、流水表，配合"分片数随时间滚动"使用。

## 3. 一致性哈希

**思路**：把哈希值空间组织成一个环（0 ~ 2³²-1），分片节点和数据都映射到环上，数据顺时针找到第一个节点归属。扩容/缩容时只影响环上相邻的一小段数据。

**例子**：3 个节点 A、B、C 均匀分布在环上。新增节点 D 落在 A、B 之间，则**只有原本属于 B 的一小段数据迁移到 D**，A、C 的数据完全不动。工程上通常给每个物理节点配 100~200 个虚拟节点，避免分布不均。

**优点**：扩容迁移量小（约 1/N 的数据），适合节点频繁变化的场景。

**缺点**：实现较复杂，路由需要缓存节点环；分片数少时可能不够均匀。

> **适用边界**：一致性哈希的价值建立在"迁移/丢失少量数据可接受"之上。数据库不像缓存可以随时丢数据，迁移数据的成本远高于缓存，所以**生产环境的 MySQL 分库分表几乎不用一致性哈希做主分片算法**，它的主战场是缓存层（如 Redis 客户端分片）。

## 4. 哈希槽（Hash Slot）

**思路**：可以看作一致性哈希的工程化变体，代表是 **Redis Cluster**。先对 key 做 CRC16 哈希，再对固定数量的槽（Redis 是 16384 个）取模，key 落到槽，槽再整体分配给节点。

**例子**：Redis Cluster 3 个主节点，16384 个槽均分：

- 节点 A：槽 0 ~ 5460
- 节点 B：槽 5461 ~ 10922
- 节点 C：槽 10923 ~ 16383

`CRC16("order:1001") % 16384 = 8732` → 落在节点 B。扩容加节点 D 时，只需从 A/B/C 各划出一部分**槽**给 D，槽内的数据整体搬走，key 到槽的映射规则永远不变。

**优点**：迁移粒度是**槽而不是单条数据**，扩缩容可控、可分批执行；槽与节点解耦，路由表小（16384 个槽的映射一屏放得下）。

**缺点**：与框架绑定强（槽机制是 Redis Cluster 内建的），通用分库分表场景很少自己实现一套槽管理。

## 5. 查表路由（映射表）

**思路**：不做数学计算，直接维护一张"分片键 → 目标库表"的路由表，查询时先查路由。**不限于号段映射，任意键都可以一对一映射**——单个用户 ID、单个租户 ID 直接指向某个库表。

**例子一（号段映射）**：把客户按地域分配：

| customer_id 段 | 归属                 |
| -------------- | -------------------- |
| 1~5000         | db_east（华东客户）  |
| 5001~9000      | db_north（华北客户） |
| 9001~          | db_south（华南客户） |

**例子二（一键一映射）**：路由表中直接记录 `tenant_1001 → db_2.t_5`，租户迁移时只改这一行路由，数据整体搬走，其他租户完全不受影响——这是查表路由优势最明显的场景。

**优点**：完全灵活，可按业务规则任意指定归属；**租户/大客户迁移成本极低**。

**缺点**：路由表本身成为查询多一跳的开销和单点，需要缓存；键值多时路由表也很大。适合分片数量少、业务规则复杂的场景。

## 6. 按时间分片

**思路**：**范围分片的特例**（本质仍是按区间划分，只是区间边界是时间），按分片键中的时间维度切表，常见于日志、账单、流水类数据。

**例子**：`t_log` 按月分表：

- 2026-09 的数据 → `t_log_202609`
- 2026-10 的数据 → `t_log_202610`

查询 `WHERE log_time BETWEEN '2026-10-01' AND '2026-10-31'` 时，中间件直接裁剪到 `t_log_202610` 一张表。

**优点**：冷热数据天然分离，历史表可直接归档或删除，运维简单。

**缺点**：当前月份的表承受全部写入（热点问题）；不带时间条件的查询会扫全部表，所以通常**与哈希组合使用**：先按 user_id 哈希分库，再按月分表。

## 7. 字符串精确分片

**思路**：不做哈希，按字符串的前缀、首字母或某个固定字段直接路由，可视为查表路由的一种特例。

**例子**：

- 按手机号前 3 位路由：`138/139` 开头的用户 → db_0，`150/151` → db_1……
- 按账号首字母路由：`a~h` → shard_1，`i~p` → shard_2，`q~z` → shard_3

**优点**：业务定向路由，规则直观，人可以看懂"哪类数据在哪"，便于按业务线做定向运维和权限隔离。

**缺点**：分布很难保证均匀，容易热点——比如某运营商号段用户暴涨、`z` 开头账号稀少，都会造成分片倾斜。**一般只用于定向隔离（如把某类大客户单独放一个库），不做主分片算法**。

## 8. 复合分片

**思路**：多个字段组合路由，常见两种形式：

1. **复合哈希**：`hash(user_id + order_id) % N`，把多个字段拼接后统一哈希。
2. **两级路由**：第一级按 `user_id` 哈希分到库，第二级按 `order_id`（或时间）分到表。

**例子**：订单表 4 库 × 8 表，采用两级路由：

- `user_id = 1001` → `hash(1001) % 4 = 1` → db_1
- `order_id = 88000123` → `hash(88000123) % 8 = 3` → db_1.t_order_3

**优点**：满足多维度路由需求；两级路由下"按用户查订单"能裁剪到单库，缩小扫描范围。

**缺点**：路由逻辑复杂；非分片键查询（如只按订单号查）基本走全分片扫描，往往需要用**基因法**补救——一句话解释：**把 user_id 的哈希低位嵌入 order_id 的低位，这样即使只拿 order_id 查询，也能从 ID 本身还原出分片位置，路由到正确的库表**。这是面试和实战中的高频追问点。

## 9. 其他小众算法

- **地理位置分片**：按经纬度网格或区域编码分片，如华北数据一个库、华东一个库。优点是就近访问延迟低、符合数据合规（数据不出境/不出区域）要求；缺点是区域间数据量天然不均，跨区域查询要聚合。常见于物流、外卖、IoT 场景。
- **租户 ID 直映**：SaaS 多租户场景，一个租户一张表或一个库，`tenant_id` 直接决定归属，本质是查表路由的极端形式。优点是租户间物理隔离、安全和性能互不影响、单个大客户可独立扩容；缺点是租户数多时元数据管理压力大，小租户独占资源浪费，通常与共享库表模式分级混用（大客户独库、中小客户共享分片）。

## 选型建议

| 场景                             | 推荐算法                                     |
| -------------------------------- | -------------------------------------------- |
| 订单、用户等业务表，追求均匀     | 哈希取模（先哈希再取模，预留足够逻辑分片数） |
| 日志、流水，按时间查询为主       | 按时间分片（范围分片的特例），可叠加哈希分库 |
| 需要频繁扩缩容的缓存层           | 一致性哈希 / 哈希槽（Redis Cluster）         |
| 分片少、归属规则复杂、租户常迁移 | 查表路由                                     |
| 按 ID/时间范围查询多             | 范围分片                                     |
| 按号段/前缀定向隔离              | 字符串精确分片（不做主分片）                 |
| 多维度查询的业务表               | 复合分片（两级路由 + 基因法）                |
| 多区域、合规要求                 | 地理位置分片                                 |
| SaaS 多租户                      | 租户 ID 直映（大小客户分级）                 |

> 说明：按时间分片在分类上从属于范围分片，表中并列只是为了方便按场景检索。

**通用原则**：

1. 分片键要选**查询条件中出现频率最高的字段**，否则大量查询无法路由裁剪，退化为全分片扫描。
2. 分片键分布不均匀时先哈希再取模，别直接 `id % N`。
3. 优先保证分布均匀，警惕写热点（范围/时间/字符串类算法都是热点高发区）。
4. 扩容代价要在设计时就想清楚——哈希取模建议一步分够逻辑片数，用"逻辑分片多、物理库少，扩容只搬库"的方式规避再哈希；能接受槽管理成本的，可借鉴哈希槽思路把迁移粒度做大。
5. 分片键之外的高频查询维度，提前规划异构索引表或基因法，不要指望上线后再补。
