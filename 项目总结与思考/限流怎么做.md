# 限流怎么做：从 OpenIM 的 BBR 到 SuIM 的实现

限流不是一个“给别人添堵”的功能，而是一种**在系统容量边界上主动做选择**的机制。

一个 IM 系统里，注册、登录、发消息、拉会话列表、建立 WebSocket 长连接都会消耗 CPU、内存、数据库连接和 Redis 带宽。如果任由流量无限进入，最坏情况不是“慢一点”，而是所有请求一起超时、线程全部阻塞、数据库连接池被打满，最终整个服务不可用。限流要做的事情就是：**在超载之前拒绝一部分请求，保住剩下的请求。**

这篇文章分两部分：

1. 介绍常见限流算法，以及 OpenIM 是怎么做的；
2. 讲 SuIM 参考 OpenIM 实现限流的设计、代码路径、部署配置和可观测性。

---

## 一、限流到底在解决什么问题

### 1.1 容量是有限的

任何一个服务都有容量上限：

- CPU：请求解析、序列化、加解密、业务逻辑都要算力；
- 内存：连接、缓存、待处理消息都占内存；
- 下游依赖：MySQL 连接池、Redis 连接池、对象存储、推送厂商都有配额；
- 锁与临界区：热点用户、热点群、热点会话会形成串行点。

如果请求速率持续高于处理能力，队列中等待的请求越来越多，响应时间变长；响应时间变长又会导致更多并发堆积，最后进入恶性循环。

### 1.2 限流与降级、熔断的区别

这三个词经常一起出现，但解决的是不同问题：

| 机制 | 关注点 | 典型动作 |
| --- | --- | --- |
| 限流 | 入口流量超过容量 | 拒绝、排队、返回 429 / `ResourceExhausted` |
| 降级 | 非核心功能拖累核心链路 | 关闭推荐、预览、回调等非关键能力 |
| 熔断 | 下游依赖持续失败 | 短时间内不再调用下游，直接失败返回 |

OpenIM 的配置里 `rateLimiter` 和 `circuitBreaker` 是并列出现的，SuIM 这次先补的是限流，熔断仍待后续实现。

### 1.3 一个好的限流器要看什么

- **判断依据**：只看 QPS，还是结合 CPU、耗时、并发？
- **作用范围**：进程内、单机、还是集群全局？
- **粒度**：全局一个桶，还是按用户、IP、接口分别限？
- **反馈闭环**：请求结束后有没有把真实耗时和结果告诉限流器？
- **可观测性**：被拒了多少？当前容量估算是多少？
- **失败语义**：被拒时客户端拿到什么错误码，能不能重试？

## 二、常见限流算法

### 2.1 固定窗口计数

把时间切成固定窗口，比如 1 秒，窗口内计数超过阈值就拒绝。

优点：简单。  
缺点：窗口边界会突刺。比如 0.9 秒来了 100 个，1.1 秒又来了 100 个，实际 200ms 内通过了 200 个请求。

### 2.2 滑动窗口计数

记录每个小桶的计数，统计最近一个完整窗口。

优点：比固定窗口平滑。  
缺点：仍然只按请求数判断，不知道系统当前是不是已经很慢。

### 2.3 令牌桶

以固定速率往桶里放令牌，请求取到令牌才放行，允许一定程度的突发。

优点：语义直观，工程上最常用。  
缺点：速率通常是静态配置；如果下游数据库突然变慢，固定速率可能仍然过高。

### 2.4 漏桶

请求先进入队列，以恒定速率流出。

优点：输出非常平滑。  
缺点：对突发不友好，需要队列和超时策略。

### 2.5 BBR 风格自适应限流

OpenIM 采用的是 BBR 思路：**不预设固定 QPS，而是用 CPU、在途请求数、历史通过数、最小响应时间动态估算当前容量。**

这套方法更适合 IM 服务，因为同一套代码在不同机器、不同数据量、不同下游状态下，承载能力可能差很多。固定 QPS 很难兼顾所有情况。

## 三、OpenIM 的限流实现

OpenIM 的限流依赖 `github.com/openimsdk/tools` 的 `stability/ratelimit/bbr`，并在两个层面接入。

### 3.1 配置模型

```go
type RateLimiter struct {
    Enable       bool
    Window       time.Duration
    Bucket       int
    CPUThreshold int64
}
```

默认配置文件里通常是：

```yaml
ratelimiter:
  enable: false
  window: 20s
  bucket: 500
  cpuThreshold: 850
```

含义：

- `window`：滑动窗口总长度；
- `bucket`：窗口切成多少个桶；
- `cpuThreshold`：CPU 阈值，0～1000，850 表示 85%；
- `enable`：是否开启。

### 3.2 gRPC 入口

OpenIM 在 `startrpc.Start` 里根据配置追加两个 interceptor：

- `UnaryRateLimitInterceptor`
- `StreamRateLimitInterceptor`

每个请求进入业务逻辑前调用：

```go
done, err := limiter.Allow()
if err != nil {
    return nil, status.Errorf(codes.ResourceExhausted, ...)
}
defer done(ratelimit.DoneInfo{})
return handler(ctx, req)
```

被拒绝时返回 gRPC `ResourceExhausted`；允许时请求结束必须调用 `done()`，否则在途计数无法归零。

### 3.3 HTTP 入口

API 网关使用 Gin middleware：

- 请求前写 `X-BBR-CPU`、`X-BBR-MinRT`、`X-BBR-MaxPass`、`X-BBR-MaxInFlight`、`X-BBR-InFlight`；
- 调用 `Allow()`；
- 拒绝时设置 `X-RateLimit-Policy: BBR`、`Retry-After`、`X-RateLimit-Limit`、`X-RateLimit-Remaining: 0`，返回 HTTP 429；
- 允许时执行 `c.Next()`，结束后调用 `done()`。

### 3.4 BBR 的判断逻辑

OpenIM 使用的 BBR limiter 核心信号：

- `gCPU`：每 500ms 采样一次 CPU，用 0.95 的 EMA 平滑，范围 0～1000；
- `inFlight`：已经放行但还没结束的请求数；
- `passStat`：滑动窗口内每个桶的通过数；
- `rtStat`：滑动窗口内每个桶的响应时间；
- `prevDropTime`：上次触发限流的时间，用于 1 秒冷却期。

核心公式：

\[
maxInFlight \approx \frac{maxPass \times minRt \times bucketPerSecond}{1000}
\]

其中 `minRt` 单位是毫秒。这个公式本质上是 Little's Law：并发容量 ≈ 吞吐 × 延迟。

判断规则：

- CPU 低于阈值：通常放行；如果刚发生过限流且在 1 秒冷却期内，则按 `inFlight > maxPass()` 继续压制；
- CPU 达到或超过阈值：如果 `inFlight > maxInFlight()` 就拒绝。

### 3.5 OpenIM 实现中值得注意的地方

1. 它是进程内限流，多副本会放大总容量。
2. 没有按用户、IP、接口维度区分。
3. `DoneInfo.Err` 没有参与计算，失败请求也算通过。
4. `Retry-After` 的实现里有 `status.CPU / status.CPU` 的自除问题，结果基本恒为 1。
5. 限流 interceptor 在 metrics interceptor 之前，被限流直接返回的 RPC 可能不会计入普通 RPC 指标。

这些观察直接影响了 SuIM 的实现取舍。

## 四、SuIM 的实现目标

SuIM 这次实现限流时定了几个目标：

1. **对齐 OpenIM 体验**：同样的配置语义、同样的响应头、同样的 gRPC/HTTP 错误语义。
2. **不引入新依赖**：不直接依赖 `openimsdk/tools`，在本仓库内实现等价核心逻辑。
3. **保留反馈闭环**：`Allow()` 返回 `done()`，请求结束必须归还。
4. **可观测**：被限流的请求有独立 Prometheus 指标。
5. **默认安全**：所有服务默认关闭，配置缺失不会改变现有行为。
6. **修正明显问题**：避免 OpenIM 中 `Retry-After` 自除导致的无效退避。

## 五、SuIM 的代码结构

### 5.1 公共契约

`pkg/ratelimit/types` 定义最小公共协议：

```go
type DoneInfo struct {
    Err error
}

type DoneFunc func(DoneInfo)

type Stat struct {
    CPU         int64
    InFlight    int64
    MaxInFlight int64
    MinRT       int64
    MaxPass     int64
}

type Limiter interface {
    Allow() (DoneFunc, error)
    Stat() Stat
}
```

单独拆出 `types` 是为了避免循环依赖：`bbr` 实现包依赖它，门面包 `ratelimit` 也依赖它。`pkg/ratelimit/ratelimit.go` 只是把这些类型重导出，业务代码仍然只 import `pkg/ratelimit`。

### 5.2 BBR 核心

`pkg/ratelimit/bbr/bbr.go` 实现自适应限流：

- 默认窗口 10 秒、100 个桶、CPU 阈值 800；
- SuIM 配置层统一使用 20 秒、500 桶、阈值 850；
- CPU 采样读取 Linux `/proc/stat`，每 500ms 更新一次 EMA；
- `WithCPUGetter` 允许在测试里注入确定性的 CPU 值；
- `WithCPUQuota` 支持按 CPU quota 缩放；
- 滑动窗口分别记录通过数和响应时间；
- 缓存按桶粒度失效，避免每个请求都扫描窗口；
- `done()` 用 `sync.Once` 包了一层，防止重复归还导致 `inFlight` 变负。

核心调用如下：

```go
done, err := limiter.Allow()
if err != nil {
    return nil, ratelimit.ErrLimitExceeded
}
return func(ratelimit.DoneInfo) {
    // 记录 RT、inFlight--、passStat++
}, nil
```

### 5.3 配置层

`pkg/config/config.go` 新增：

```go
type RateLimiter struct {
    Enable       bool          `yaml:"enable"`
    Window       time.Duration `yaml:"window"`
    Bucket       int           `yaml:"bucket"`
    CPUThreshold int64         `yaml:"cpuThreshold"`
}
```

`Validate()` 负责补齐默认值并检查：

- `window` 默认 20s；
- `bucket` 默认 500；
- `cpuThreshold` 默认 850；
- `cpuThreshold` 必须在 0～1000；
- `window / bucket` 必须至少为 1ns。

12 个服务的内部配置都增加：

```go
RateLimiter config.RateLimiter `yaml:"rateLimiter"`
```

并在各自的 `Validate()` 开头调用 `c.RateLimiter.Validate()`。

### 5.4 gRPC 拦截器

`pkg/ratelimit/middleware.go` 提供：

```go
func UnaryServerInterceptor(serviceName string, cfg *config.RateLimiter) grpc.UnaryServerInterceptor
func StreamServerInterceptor(serviceName string, cfg *config.RateLimiter) grpc.StreamServerInterceptor
```

行为：

1. 配置关闭时直接透传；
2. 调用 `limiter.Allow()`；
3. 拒绝时记录 `rate_limit_rejected_total{service,kind="grpc"}`，返回 `ResourceExhausted`；
4. 允许时执行业务 handler，并通过 `done(DoneInfo{Err: err})` 归还。

接入的服务：

- `user`
- `group`
- `third`
- `relation`
- `conversation`
- `msg`
- `msggateway`
- `push`
- `rtc`

拦截器放在 `mw.UnaryRecover` 和业务 handler 之间、Prometheus interceptor 之前，和 OpenIM 的保护顺序一致：

```go
grpc.ChainUnaryInterceptor(
    mw.UnaryRecover,
    ratelimit.UnaryServerInterceptor("user", &cfg.RateLimiter),
    prommetrics.UnaryServerInterceptor("user"),
)
```

### 5.5 HTTP 中间件

HTTP 侧提供：

```go
func HTTPMiddleware(serviceName string, cfg *config.RateLimiter) func(http.Handler) http.Handler
```

接入点：

- `apigateway`：包在 `GzipHandler` 外、`prommetrics.HTTPMiddleware` 内；
- `msggateway`：包在 `CorsHandler` 外、`RecoverHandler` 内。

拒绝时返回：

- HTTP 429；
- JSON body：`{"code":1009,"msg":"too many requests, please try again later"}`；
- `X-RateLimit-Policy: BBR`；
- `Retry-After`；
- `X-RateLimit-Limit`；
- `X-RateLimit-Remaining: 0`；
- `X-BBR-CPU` / `X-BBR-MinRT` / `X-BBR-MaxPass` / `X-BBR-MaxInFlight` / `X-BBR-InFlight`。

业务错误码 `1009` 对应 `errorcode.ErrRateLimited`，其 gRPC code 是 `ResourceExhausted`。

## 六、和 OpenIM 的差异与取舍

| 维度 | OpenIM | SuIM |
| --- | --- | --- |
| 依赖 | 外部 `openimsdk/tools/bbr` | 本仓库 `pkg/ratelimit/bbr`，无新依赖 |
| CPU 采样 | 依赖工具包内部采样 | 直接读 `/proc/stat`，每 500ms EMA |
| 配置默认值 | 代码默认 10s/100/800，配置覆盖为 20s/500/850 | 配置层统一默认 20s/500/850 |
| 公共类型 | 接口在 tools 包内 | 独立 `pkg/ratelimit/types` 解耦 |
| `DoneInfo.Err` | 传空结构体 | gRPC 传真实 err，HTTP 暂传空；BBR 暂不用 |
| `done()` 幂等 | 未显式保护 | `sync.Once` 保护 |
| `Retry-After` | 自除 bug，基本恒为 1 | 按 CPU 区间返回 1/2/3/5 秒 |
| 限流指标 | 无专门指标 | `rate_limit_rejected_total{service,kind}` |
| 作用范围 | 进程内 | 进程内 |
| 维度 | 全局一个 limiter | 全局一个 limiter |

保留“进程内、全局一个 limiter”的原因：先和 OpenIM 对齐，保持实现简单。后续如果要做按用户/IP/接口的精准限流，可以在 middleware 里按 label 选择不同 limiter，而不是在 BBR 核心里塞业务维度。

## 七、Kubernetes 配置

`deployments/configmap.yml` 的 12 个服务配置都加了：

```yaml
rateLimiter:
  enable: false
  window: 20s
  bucket: 500
  cpuThreshold: 850
```

默认关闭，升级不会突然改变线上行为。

需要开启时，只改对应服务的 `enable: true`，或者按需调整窗口、桶数和 CPU 阈值。

需要特别注意：

- 每个 Pod 都有自己的 limiter；
- 如果 apigateway 有 3 个副本，每个 Pod 都按自己的 CPU 和窗口判断；
- 全局 QPS 上限约等于单 Pod 容量 × 副本数；
- 真正的集群级限流需要 Redis 计数、网关层限速或 Service Mesh。

`msgtransfer` 和 `crontask` 没有入站 RPC/HTTP，配置虽然存在，但当前不生效。它们更适合用消费者并发度、批量大小和 worker 数控制。

## 八、可观测性

新增指标：

```text
rate_limit_rejected_total{service,kind}
```

`kind` 取值：

- `grpc`：unary RPC 被拒；
- `stream`：stream RPC 被拒；
- `http`：HTTP 请求被拒。

常用 PromQL：

```promql
# 每个服务每秒被限流多少次
sum by (service) (rate(rate_limit_rejected_total[5m]))

# apigateway HTTP 限流趋势
sum(rate(rate_limit_rejected_total{service="apigateway", kind="http"}[1m]))

# 对比 HTTP 429 与限流拒绝
sum(rate(http_count{status="429"}[5m])) by (path)
sum(rate(rate_limit_rejected_total{kind="http"}[5m])) by (service)
```

排查问题时可以结合响应头：

- `X-BBR-CPU` 高：CPU 已经达到阈值，系统在主动收缩；
- `X-BBR-InFlight` 接近 `X-BBR-MaxInFlight`：并发已经接近估算容量；
- `X-BBR-MinRT` 变大：下游或系统本身变慢，`maxInFlight` 会随之下降；
- `Retry-After` 变大：CPU 压力较高，客户端应拉长重试间隔。

## 十、局限与后续方向

当前实现仍然有几个明确边界：

1. **不是分布式限流**  
   多 Pod 容量会叠加，无法给出集群级硬上限。

2. **没有按身份维度限制**  
   一个用户、一个 IP、一个接口都共享同一个 limiter。恶意用户和正常用户会被同等对待。

3. **CPU 采样依赖 Linux `/proc/stat`**  
   在非 Linux 环境 CPU 会保持为 0，此时主要依赖窗口容量判断；生产 Kubernetes 节点是 Linux，不受影响。

4. **失败请求仍计入 pass**  
   和 OpenIM 一样，BBR 目前只看耗时，不看业务结果。未来可以让 `DoneInfo.Err` 参与统计，例如 5xx 或下游超时算作负反馈。

5. **消费者服务未接入**  
   `msgtransfer`、`crontask` 更适合用并发度和批处理参数控制，而不是入站限流。

后续可以做的方向：

- 按服务、接口、用户维度建立 limiter 表；
- 用 Redis + Lua 实现全局滑动窗口；
- 在网关层做第一层粗粒度限流，服务内 BBR 做第二层保护；
- 将 `rate_limit_rejected_total` 接入告警；
- 根据 `Retry-After` 做客户端指数退避 + jitter；
- 和熔断联动：下游连续失败时直接降低 `maxInFlight`。

## 十一、总结

限流的核心不是“把请求挡住”，而是**在容量边界上做有依据的取舍**。

OpenIM 提供了一套很实用的工程范式：用 CPU、在途数、通过数和响应时间共同判断系统容量，而不是死守一个静态 QPS。SuIM 这次参考它实现了：

- 可配置、默认关闭的 BBR 限流；
- gRPC unary/stream interceptor；
- HTTP middleware；
- 与 OpenIM 对齐的 429/ResourceExhausted 语义和响应头；
- 独立限流 rejection 指标；
- 12 个服务的配置与 Kubernetes ConfigMap；
- 默认关闭、可灰度开启的安全升级路径。

这套实现保留了 OpenIM 的自适应思想，同时修掉了几个明显问题。它不是最终形态，但已经足以让 SuIM 在流量突增时**先保护自己，再谈吞吐量**。
